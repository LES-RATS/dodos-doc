## Findings

### 1. [Major] Staggered fresh start enables `watch_own_cores` before secondary cores enter, triggering false `CoreSilent` self-accusation before `START_NS`
- **File & line at `6b657e4`:** [`model/src/cores.rs:942-943`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/cores.rs#L942-L943) and [`model/src/cores.rs:703-726`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/cores.rs#L703-L726) (commit `42d1ad9`).
- **Contract line:** [`kernel-interface.md:1668`](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L1668) ("for *X* starting, now − *t* ≥ `START_NS` ... since its cores may take longer than `STALE_NS` to reach its first event"), [`kernel-interface.md:1657`](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L1657), [`kernel-interface.md:1675`](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L1675).
- **What is wrong:** Fault #2's fix adds `self.beat_on(position)` when `late.is_empty()` in `Model::core_entered` (`cores.rs:932`), which only clears a reused core's stale `idle_until = 0` once that core reaches `core_entered`. However, on a fresh start (`!self.resuming`), when core `position == 0` enters `core_entered` first, `cores.rs:942-943` unconditionally sets `self.ready = true` even while secondary cores (`position >= 1`) are still `Joining` (`core.silent == true`) and have not yet run `core_entered`. Meanwhile `watch_own_cores` (`cores.rs:706-725`) checks `if self.width() == 1 || !self.ready || self.table.release { return; }` and iterates over *every* `(0..self.width()).filter(|&p| p != at)` without skipping un-entered (`cores[position].silent`) or `Joining` cores while the node is `Starting`. If a secondary physical core was previously busy when an earlier generation died (`core_beacons[number].idle_until.0 == 0`), and core 0 runs events for `STALE_NS` (40 ms) before the secondary core enters `core_entered` (which is allowed up to `START_NS` = 1000 ms), `watch_own_cores` observes the stale `heartbeat` and `idle_until == 0` on that secondary core and falsely accuses the healthy `Starting` node (`CrashReason::CoreSilent = 9`).
- **Concrete scenario:** In scratch `review_repros::exp_2b_staggered_fresh_start_falsely_self_accuses_before_start_ns`:
  1. Node 1 holds cores `[1, 2]`. Secondary core 2 runs a thread so `core_beacons[2].idle_until.0 == 0`, then node 1 is killed and reclaimed while core 2's beacon stays `idle_until == 0`.
  2. Node 0 issues `fresh(1, 0b110)`. Core 1 (`position == 0`) enters `core_entered` first (`self.ready = true`, node 1 still `MemberState::Starting`, core 2 still `Joining` and `silent == true`).
  3. Advancing 80 ms (`STALE_NS < 80 ms << START_NS`) while holding core 2's start events triggers `watch_own_cores` on core 1: node 1 falsely accuses itself with `beacons[1].panic == Some((9, 2, 1))` (`CrashReason::CoreSilent`), killing a healthy starting node ~920 ms before `START_NS`.

### 2. [Major] Checks 43 and 47 accept `at >= self.now` unconditionally and exempt any `core.silent` without cross-checks
- **File & line at `6b657e4`:** [`model/src/check/sched.rs:92-95`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/check/sched.rs#L92-L95) (check 43) and [`model/src/check/sched.rs:247-251`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/check/sched.rs#L247-L251) (check 47) (commit `7ec0b29`); missing cross-check in [`model/src/check/machine.rs:249-269`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/check/machine.rs#L249-L269).
- **Contract line:** [`kernel-interface.md:634`](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L634), [`kernel-interface.md:636`](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L636) (`timer_set`: "if *f* is not after now the timer fires in this call, before it returns"), [`kernel-interface.md:641`](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L641) (`TIME_EVENT_STEP = 16` per timer interrupt), [`kernel-interface.md:2136`](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L2136).
- **What is wrong:** Commit `7ec0b29` relaxed both checks in two ways that are wider than the contract allows:
  1. **Unconditional `at >= self.now`:** A timer or replenishment at `== self.now` is lawful *only* when `TIME_EVENT_STEP` (`16`) due events were already processed on that core at `self.now` (or on another core at the same `now` awaiting its timer interrupt). Accepting `at >= self.now` unconditionally means `TimerSet` or `due()` can fail to fire/replenish an `== now` event even when zero due events have been served, and `check()` passes silently.
  2. **Unconstrained `core.silent` in check 47:** Check 47 now exempts `armed.core` whenever `core.silent` is true (`sched.rs:247, 249`), matching check 43 (`sched.rs:84`). However, `check_machine` (`check/machine.rs:249-269`) only asserts `!is_silent => Owned | Joining` for `Hardware::Running` cores; it never asserts the converse (`Hardware::Running => !is_silent` once entered, or that `silent` implies the core is stopped/unentered). Neither `check_sched` nor `check_cores` bounds `core.silent`. A model bug leaving `core.silent = true` on an actively running core hides indefinitely overdue timers (and overdue replenishments under check 43).
- **Concrete mutations & reproducer:**
  - *Mutation 1 (same-instant firing bug):* Mutate `Model::timer_set` in [`model/src/sched.rs:1143`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/sched.rs#L1143) from `if instant <= self.now` to `if instant < self.now` and call `TimerSet { deadline: now, tolerance: 0 }` on a single-core idle node. Before `7ec0b29` (`armed.instant > self.now`), `m.check()` catches the contract violation with `Err("47: armed timer")`. Under `6b657e4` (`armed.instant >= self.now`), `m.check()` returns `Ok(())` even though no `TIME_EVENT_STEP` cap was reached and contract line 636 requires immediate firing. (The same applies if `Model::due` at `sched.rs:727, 732` uses `instant < now`.)
  - *Reproducer 2 (silent-core timer exemption):* In scratch `review_repros::exp_1b_silent_core_exempts_past_timer`, setting `k.m.cores[0].silent = true` on a running core with an armed timer 50 ms strictly in the past produces `k.m.check() == Ok(())`.

### 3. [Major] Unconstrained `core.asleep > 0` exemption in `CORE_ANSWER_NS` invariant
- **File & line at `6b657e4`:** [`model/src/check/node.rs:374-380`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/check/node.rs#L374-L380) (commit `42d1ad9`), and missing cross-check in [`model/src/check/machine.rs:240-248`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/check/machine.rs#L240-L248).
- **Contract line:** [`kernel-interface.md:1918`](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L1918), [`kernel-interface.md:2281`](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L2281), [`kernel-interface.md:2337`](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L2337).
- **What is wrong:** `Model::check_cores` allows a request past `started + core_answer_ns` up to `due.saturating_add(core.asleep)` whenever `core.asleep > 0`, without verifying that the requesting core is actually sleeping/waking (`core.thread.is_none()` / `Hardware::Suspending | Hardware::Asleep` in `System`). `check_machine` (`check/machine.rs:240-248`) checks only that a sleeping hardware core runs no unwoken thread, never that a `Hardware::Running` (or thread-running) core has `core.asleep == 0`. Thus a model bug that fails to clear `core.asleep` on wake (or sets `asleep` on an awake core) suppresses `CORE_ANSWER_NS` timeout detection past `started + core_answer_ns` on an awake requester. (Notably, unlike the contract's `node_idle` margin rule at `kernel-interface.md:2281`, if a large `core.asleep` were ever left set it would also push `due.saturating_add(core.asleep)` arbitrarily far.)
- **Concrete reproducer:** In scratch `review_repros::exp_1c_nonzero_asleep_exempts_core_answer_ns_on_awake_core`, an awake running core 0 holds a 10 ms `core.asleep` value and has an unanswered `ASpaceUnmap` request to core 1 at `started + CORE_ANSWER_NS + 5 ms`. The node did not self-accuse, yet `m.sys.check()` returns `Ok(())`.

### 4. [Minor] Harness bound and refusal counters in `bounds.rs` have false-positive triggers
- **File & line at `6b657e4`:** [`model/src/scenarios/bounds.rs:304-306, 509-518, 668-670, 859-875, 878-917, 980-989`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/scenarios/bounds.rs#L304-L306) (commits `e1f1460`, `e43814a`).
- **What is wrong:** Multiple counters in `bounds.rs` conflate unrelated errors, setup calls, or cross-node states with reaching a specific contract bound. Auditing the table rows in `/private/tmp/pass43-report.md` found false positives in at least 8 rows (6 reproduced directly in `review_repros`):
  1. **Row 12 — `recovery_period_waited` (`bounds.rs:304-306`):** `if node.steps_at.0 > 0 { self.recovery_period_waited = true; }` triggers on the *first* `reserve_step()` at any `now > 0`, even when no wait for the 10 ms period ever occurred. *Reproducer (`exp_3a_recovery_period_waited_false_positive`):* after `kill(1)` + `settle(1)` at `now = 1_000 ns` (`0.0001 × RECOVERY_PERIOD_NS`), `bounds.recovery_period_waited` is already `true`.
  2. **Row 28 — `cspace_over_max_refused` (`bounds.rs:907-917`):** Any `CSpaceGrow` returning `Err(Error::NoSlot)` or `Err(Error::Busy)` sets `cspace_over_max_refused`, even on a 256-slot CSpace far below `CSPACE_MAX_SLOTS = 2^20` (and even when `Busy` comes from an in-flight removal). *Reproducer (`exp_3b_cspace_over_max_false_positive`):* growing a 256-slot CSpace past 256 returns `Err(Error::NoSlot)` and sets `bounds.cspace_over_max_refused == true`.
  3. **Row 40 — `clear_step_again` (`bounds.rs:878-881`):** Any `UntypedRetype` returning `Err(Error::Again)` sets `clear_step_again`, including small objects waiting for a multi-core watermark barrier (`cores.rs` / `memory.rs`). *Reproducer (`exp_3c_clear_step_again_false_positive`):* retyping a 64-byte `Notify` from a 4096-byte child untyped whose parent wait needs a TLB watermark barrier returns `Err(Error::Again)` and sets `bounds.clear_step_again == true` nowhere near `CLEAR_STEP_BYTES = 65536`.
  4. **Row 37 — `tree_depth_65_refused` (`bounds.rs:888-905`):** Any `UntypedRetype` or `CapDerive` returning `Err(Error::Invalid)` anywhere on the node sets `tree_depth_65_refused` whenever *any* unrelated capability in `model.caps` has `depth >= TREE_DEPTH`. *Reproducer (`exp_3d_tree_depth_65_false_positive_invalid`):* after deriving one capability to depth 64, issuing an unrelated invalid `UntypedRetype` of a `0`-page `Frame` sets `bounds.tree_depth_65_refused == true`.
  5. **Row 30 — `sweep_2_sealed_capped` (`bounds.rs:509-518`):** Sets `true` whenever `others_sealed >= 3 && node.next_sweep > table.sweep_ns`. That fires as soon as 3 nodes are sealed *after any earlier sweep*, even before a single sweep runs while 3 nodes are sealed. *Reproducer (`exp_3e_sweep_2_sealed_capped_false_positive`):* advancing past one sweep (`105 ms`), sealing nodes `1, 2, 3`, and running only `5 ms` (so no sweep runs with 3 sealed nodes) sets `bounds.sweep_2_sealed_capped == true`.
  6. **Rows 3 & 8 — `stale_starting_accused` & `start_timeout` (`bounds.rs:980-989`):** Checks `model.starts.values().any(|s| s.generation == g)` across all entries in `model.starts` instead of `model.starts.get(&node_idx)`. If node `X` is `Starting` at generation `g` while a different `Live` node `Y` at the same generation `g` becomes `Fencing(Stale)`, node 0 attributes `Y`'s accusation to a `Starting` timeout. *Reproducer (`exp_3f_stale_starting_accused_false_positive`):* node 2 is `Starting` at generation 2 (unharmed), node 1 becomes `Live` at generation 2, hangs core 1, and goes `Fencing(Stale)` -> `bounds.stale_starting_accused == true` and `bounds.start_timeout == true`.
  7. **Rows 20 & 26 — `removal_32_again` & `req_credit_17th_refused` (`bounds.rs:668-670, 859-875`):** `CallMeta::Removal` `Err(Error::Again)` sets `removal_32_again` (and `Body::RevokeStep { removed: false }` sets it too), and sets `req_credit_17th_refused` whenever any peer has 16 credits—conflating `REMOVAL_SLOTS = 128`, `Record::Unmapping`, `Wait::Pending`, and remote `RevokeStep` waiting with the 32-unit step or 17th-credit path. (Similarly, `bounds.rs:602-615` sets `kernel_ring_hit_reserve` whenever `k_used >= 30` and any queued work targets `to`, even if no `ring_room` reserve check actually refused a send.)

## Cross-Node Recovery Gaps Remaining (Item 5)

In `/private/tmp/pass43-report.md` (table + §6), heavy caps are isolated inside single-purpose `pass43.rs` tests while the long combination run keeps them at `NO` (`RING_KERNEL_ENTRIES` full / `RING_ANSWER_RESERVE` used, `REQUESTS_PER_PEER = 16` + 17th refused, `UNIT_REQUESTS = 64`, `GRANTS = 4096` / `uses_dropped`, `PENDING_STEP = 32`, `SCHED_MAX_DEBT`, `TIME_EVENT_STEP` across samples, `MAP_COUNT_MAX`, and scaled `NODES_MAX` / `CORES_PER_KERNEL_MAX`). Several of these could hide cross-node recovery bugs if combined with a node death, fence, or rebuild:

1. **Full kernel ring (`64` entries with `RING_ANSWER_RESERVE = 34` used) + `REQUESTS_PER_PEER = 16` / `UNIT_REQUESTS = 64` during holder or peer death:**
   - *Interleaving:* Node `A` saturates `A -> B` at 64 entries (`30` requests + `34` answers) and holds `16` open request credits to IOMMU holder `B` (and/or `64` entries in `unit_requests`). Peer `C` kills or fences `B`, or `B` seals and resumes (`resume=1` keeping consumer indices) while `C` concurrently dies and needs `R0`/`R5`/`R6` or `RoleHand` traffic across the same saturated rings. Because `long_run` only reaches `k_used = 30` and `req_credits = 2`, the combination of full answer-reserve consumption + credit cancellation + `RoleHand` / multi-ask `Report` rebuilds is never explored.
2. **`GRANTS = 4096` (full grant/use tables and `uses_full_dropped`) during death, fence, and `R6` reclaim:**
   - *Interleaving:* Granter `G` grants 4,096 frames to borrower `U` (and/or fills `uses[U]` to 4,096 so `SendAnswer { dropped: true }` occurs); `U` is killed or hangs into `Fencing`/`Unfenced`, or `G` dies while `U` holds 4,096 `maps_of` entries. `R2`/`R3`/`R5`/`R6` must drain >128 `REMOVAL_STEP` chunks across many recovery periods without dropping `maps_of` tracking early or overflowing `G <-> U` rings when releasing grants concurrently with a fresh start of `G` or `U`. (`long_run` stays at `36/32` grants/uses.)
3. **`PENDING_STEP = 32` (>32 `release_pending` / `signal_pending`) interrupted mid-flush by peer death and fresh start:**
   - *Interleaving:* Borrower `U` accumulates 36 `release_pending` (and 36 `signal_pending`) entries targeting granter `G`. On one `reserve_step`, `send_pending()` flushes the first 32 (`rings.rs:870`), leaving 4 pending. Before `U`'s next `reserve_step`, `G` dies, is fenced, and fresh-starts (`generation = g + 1`) — or `U` seals and resumes. The remaining 4 entries must observe `G`'s ended generation, avoid sending stale releases to `g + 1`, and still clear `U`'s `maps_of` / finish `R6` reclaim of `G(g)`. (`long_run` reaches only `sig=2, rel=6`.)
4. **`TIME_EVENT_STEP = 16` interacting with `SWEEP_NS`, `FENCE_NS`, and `START_NS` timers:**
   - *Interleaving:* Core 0 of a driver/sweeper node has ≥16 user timers/replenishments due at the same `now` as `next_sweep`, a `Fence` round timer, or a `Start` retry timer. Because `due()` (`sched.rs:737`) takes at most 16 sorted events (`(instant, rank, entered)`), multiple same-instant events could defer `FENCE` or `SWEEP` wakeups across interrupts, risking missed `FENCE_NS` or `SWEEP_NS + STALE_NS` windows under timer saturation.
5. **Multi-core scaling (`CORES_PER_KERNEL_MAX` > 2) and `MAP_COUNT_MAX` with remote grants:**
   - *Interleaving:* All combination runs cap `WIDE` at 2 cores, missing ≥3-core staggered `core_entered` / TLB shootdowns where two running cores observe a third un-entered or hung core; similarly `MAP_COUNT_MAX` is never exercised alongside remote `Grant` / `ASpaceMap` + `R6` `check_counts` reclamation on a dying node's chunk.
