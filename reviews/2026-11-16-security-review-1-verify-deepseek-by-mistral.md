## Findings, verdicts

### Finding 1 — the `private` mark has no rule that sets it. **Verdict: confirmed, narrowed by the contracts.**

Quotes verified (see above). The attack follows from the text: 184 defines the two marks, 186 defines propagation, 187 defines who is trusted, and no line states a trigger for `private`; the only trigger sentence is inside a scenario (295, "It reads the file, which adds `private`"), which 186+187 do not back for a `user`-origin store object, since 187 makes the user's own data trusted (absence of `untrusted`) and nothing stamps `private` at write time. Step by step: bill read as a store object (row 202, automatic) adds no mark; page read adds `untrusted`; external read in a task marked `untrusted` but not `private` is automatic (205); the figures leave in the address (178's own residual: "data carried in the address"). That is exactly scenario 2 (296), which the page says stops at the confirmation — it stops only if `private` was set, and nothing sets it. Not settled by any decision (D-035 at decisions/README.md:45 decides that two marks exist, not what sets `private`) and not listed as pending (I grepped pending-decisions.md for "private": only P-037/P-038/P-041 touch it, none about the trigger).

**What the contracts say.** Partly closing. core.wit:159-162 defines `private` as "derived from the user's private data". agent.wit:163-167 stamps every memory entry with the writing task's marks **plus `private`** ("the memory is the user's data"). agent.wit:285-288 makes reading **any surface's accessibility tree** add `private` always ("since what the user's screen shows is the user's") and `untrusted` unless the owner is the system. So the screen-read path (scenario 1's path) and the memory path are covered in the contract. **Not covered:** the store-object path — store.wit:42-43 stamps an object only with "who wrote, under which marks", and a `user`-zone write carries no `private`. So the reviewer's attack stands only for objects read as store objects (row 202), not for content read off the screen. The finding is confirmed but narrower than stated.

**Smallest rule.** Right in substance and it breaks no legitimate task: `private` only ever matters together with `untrusted` in one matrix cell (205, and 278 says the `untrusted` mark changes only that one decision), so stamping the user zone `private` adds confirmations exactly where D-036 wants them and makes no task impossible — external reads in unmarked tasks stay automatic. The rule should name the store-object path explicitly (the screen path is already in the contract).

**External claims.** EchoLeak (arXiv 2509.10540, read today): abstract says "a zero-click prompt injection vulnerability in Microsoft 365 Copilot that enabled remote, unauthenticated data exfiltration via a single crafted email" — CVE-2025-32711 (NVD/Tenable: "Ai command injection in M365 Copilot allows an unauthorized attacker to disclose information over a network", published 2025-06-11, named EchoLeak). One crafted mail, no interaction, data leaves in a request the assistant chose — the reviewer's shape is correct. Willison (read today, 16 June 2025): "If a tool can make an HTTP request—to an API, or to load an image, or even providing a link for a user to click—that tool can be used to pass stolen info[rmation] out" — so "the ability to externally communicate" does cover an external read; the reviewer's use is correct.

### Finding 2 — an object the task holds is invisible to the matrix. **Verdict: confirmed, with one correction.**

Quotes verified. The attack follows: the mail marks the task `untrusted`; the tax return arrives as a bound object from a local read (row 202, automatic), and 189 ("Passing an object from one action to the next without reading it adds no mark") plus the contract's identical rule (actions.wit:103, "Handing adds no mark; reading an object adds its marks") mean the task holds private data with no `private` mark; an action declared `none`/`external` taking the object puts its bytes in the GET path/query (178's residual), the cell at 205 fires automatic, and the task has combined untrusted content, held private data and external communication with no confirmation — the one combination D-036 (222) forbids.

**Correction.** Objects *do* carry marks — 283 says they are "stamped with the writer's marks at each write", store.wit:42-43 implements that, and agent-written objects carry the writing task's marks. The gap is not that objects are unmarked; it is that **binding** an object to a call does not add its marks to the task (189, actions.wit:103). The contract already has the machinery to fix it: `bound` records the object id **and the version** (actions.wit:138-140). Also, the reviewer's supporting quote security.md:366 ("No copy of the input as confirmed") is outdated against the current contracts: actions.wit:146-149 keeps "the input exactly as invoked, which is exactly what the user confirmed", with secrets written as null.

**Smallest rule.** Right, and the cost is bounded: the only mark-dependent cell is the external read in an `untrusted` task (278), external modifications are confirmed whatever the marks (206, 278), so adding bound objects' marks to the matrix adds confirmations only where D-036 requires them; no task becomes impossible. The anti-creep rule 189 exists against label creep (weakness 1, 279), but 189 can stay for the planner's own reading — the fix is at binding time, not at reading time.

**FIDES claim.** "FIDES's hidden variables keep the value hidden from the planner and still taint it" — supported in substance: the paper (arXiv 2505.23643v2, 3 Sep 2025; abstract read verbatim today: "tracks confidentiality and integrity labels, deterministically enforces security policies, and introduces novel primitives for selectively hiding and revealing information") stores tool results in label-gated variables and reveals them through a quarantined LLM (confirmed via search snippets of the PDF text). The full text is not reachable from this environment (see sources section), so section numbers 5.1/5.2 stay unverified — the reviewer said so honestly.

### Finding 3 — a secret field reaches a `local`, `reversible` action with no confirmation. **Verdict: confirmed, with one correction.**

Quotes verified. The attack follows: 188 hands the secret value to the action when the button is activated; the matrix has five rows (200-206) and none is "receives a secret"; row 203 runs a local reversible modification automatically in both columns; so a card drawn by the model with a `secret` field and a button bound to a reversible local action delivers the password to the third-party application with no confirmation. The page's own note at 373 presumes a confirmation ("the confirmation of an action that receives a secret must name the receiving application first"), so two lines cannot both hold — the contradiction is real.

**What the contracts say.** They repeat the presumption in three places — catalog.wit:98-99 ("The confirmation of an action that receives a secret names the receiving application first"), manifest.wit:32-35 (os-secret "shown masked in a confirmation, written as null in the journal"), actions.wit:205-208 ("names the receiving application first") — while the matrix comment (actions.wit:196-203) has no secret condition. So the contracts **close part of the lack** (catalog.wit:94-99: a secret field on the agent's overlay is refused while the task is marked `untrusted`, and in an unmarked task is accepted only if all buttons reading it invoke actions of one application, "which the system names beside the field") but **not the core gap**: no rule forces a confirmation when a secret is handed over. **Correction to the reviewer:** "no name anywhere that says where it went" is wrong at contract level — the system names the single receiving application beside the field, and the confirmation names it first when drawn. The gap is the missing confirmation, not the missing name.

**Smallest rule.** Right, and it breaks no task: a password entry is confirmed once, and the grant (217) covers repeats in an unmarked task. The contract's field limits (single application, named) should be kept alongside.

### Finding 4 — administration actions have no effect class. **Verdict: confirmed in substance, wrong in one premise.**

Quotes verified. **Premise correction:** the contracts *do* assign classes to system-service actions — actions.wit:1-2 ("System services (settings, windows, network, install, power) export the same interface"), shell.wit:7-8 ("The effect class of each action is stated on its first record"), manifest.wit:96 (`effect` required on every action), and the shell's manifest is signed by the project. What security.md itself never says is that the class of an administration action is enforced only by the matrix: a settings change does not flow through the storage and network imports that 177 links (contract core.wit:262-282 bounds filesystem/sockets/http/background), so for these actions the declared class is a label the matrix alone enforces. The attack therefore stands as written: under P-040 option A (pending-decisions.md:714, "everything minus exclusions", recommended) the settings actions are in the task's scope; a `set-hold 0` declared `reversible`/`local` (the natural declaration, 218 allows 0) runs automatically in both matrix columns (row 203), and the ten-second hold — one of the "two levers" (323) — is gone for the session. Not settled by any decision; P-023 (pending-decisions.md:495-499) asks where system-service actions *run*, not what class they carry or how they are confirmed.

**Smallest rule.** The fixed table is right and makes no legitimate task impossible (granting a right or installing a package just gets confirmed, with provenance, row 204). A smaller alternative exists: exclude from the automatic cells any action of a system service that touches an indicator, a confirmation, a hold or a mark — same effect, less text.

### Finding 5 — the confirmation draws third-party words in system material. **Verdict: confirmed.**

Quotes verified. The attack follows: 208 draws the confirmation "from the typed schema of the action and the exact input, never from the text of the model" — it forbids the model's text only; 179 declares the schema the publisher's text; manifest.wit:14-18 includes `title` and `description` in the drawable schema subset, so a hostile publisher's property titles are drawn in glass; and 206 requires "exact content displayed", so the attacker's own words (the mail body) are necessarily drawn too. ui.md:68 teaches that glass is reserved for the system and cannot be imitated, so the trust travels with the material to the words inside it. No line on the page keeps third-party strings out of system material — every other defence is about drawing (glass, refused icon names at 302, opaque frames) or about text outside system material (299, 305). Confirmed.

**Smallest rule.** The reviewer's rule (values as quoted data in application material carrying the producer's name; system material carries only identity/class/effect) is a real design change and breaks no task — the user still sees everything that will be sent, and the frame says who produced it. A smaller rule also works and is closer to the current text: draw the application id, action name, class, argument names and exact values in glass, but never schema `title`/`description` — drop publisher prose from the confirmation, keep the data.

### Finding 6 — "a key while it holds the focus" answers the confirmation. **Verdict: confirmed as a contradiction/unsettled case, with a correction to the proposed rule.**

Quotes verified. 214 lets "a key while it holds the focus" answer; 215 is titled "Not answerable by accident" but guards only "its buttons" (500 ms) and the pointer ("never appears under the pointer"). ui.md:109 ("Only the focused surface receives keys") and ui.md:17 (compositor owns focus) mean that if the confirmation holds the focus, any key reaching it after 500 ms answers it; the page never says which key answers, nor whether appearing steals the focus — so a user typing in an editor whose next keystroke lands on a focused confirmation is the accident 215 promises cannot happen. Confirmed.

**Correction to the smallest rule.** As written it is self-contradictory: "the confirmation never takes the focus" plus ui.md:109 ("only the focused surface receives keys") means no key could ever reach it, so keyboard-only answering becomes impossible. The rule needs the focus mechanics: the confirmation takes the focus only when the user moves it there, only its own drawn key (Return or Space) answers, and a keystroke that began before it appeared cannot reach it.

### Finding 7 — a grant survives the mark that arrives after it. **Verdict: confirmed as an unsettled case; the sibling is closed by the contract.**

Quotes verified. 217 grants "until the task ends" with "Never beyond the task, never in a marked task" as a present-tense condition on granting; 186 says marks are only ever added; 278 says irreversible and external modifications "are confirmed whatever the marks". Two readings persist — the grant dies at the mark, or it does not — and the page does not choose. The contract repeats the same ambiguity (actions.wit:211-213: "for the rest of a task not marked `untrusted`, so a repeat runs without asking"). **Sibling correction:** the grant binds "these exact arguments", and the contract pins an object argument to the version the grant named (actions.wit:138-140, `bound` carries id and version), so "an argument may be an object whose content changes between calls" is closed at contract level — the grant cannot be replayed against a new version.

**Smallest rule.** Right ("a grant is withdrawn the moment the task takes a mark") and breaks nothing: the user re-confirms once per marked task.

### Finding 8 — the undo that justifies the automatic reversible cell dies with the task. **Verdict: partly right.**

Quotes verified. Right part: the journal is inside the task (160, "Nothing survives it"; store.wit:174 "Not imported by the agent: nothing survives a task"), so revoking the task — the protection 160 counts — removes the one-click undo of the automatic reversible cell (203, 224). Wrong part: "what is left is the store's version history" understates what the contract guarantees. store.wit:26-30: "every version a journal entry needs to undo stays readable while that entry is undoable"; store.wit:82-84 `at(version)` gives a read-only handle on a retained version; store.wit:127-129: remove is "Reversible through the system's version history". So during the task the undo is contract-guaranteed; after revocation the versions survive under the retention policy (P-059, pending-decisions.md:940-950, undecided), and the user's own object handle can still read them — but no agent interface restores them after the task ends, and the retention that keeps them is undecided. The gap is real but narrower: the matrix's "can be undone" (203, 224) holds only while the task lives, and nothing bounds that lifetime against P-059.

**Smallest rule.** Refine, not replace: keep "the undo is a version in the store, not only a journal entry", but state that the store guarantee covers the task's lifetime, that retention (P-059) must be decided before the matrix may rely on undo, and that a retained version remains restorable from the user's own handle after revocation.

### Finding 9 — a run-time tool catalogue has no manifest, so its actions have no class. **Verdict: wrong at the contract level — closed by mcp.md; the MCP-spec and ArtCraft claims are verified.**

Quotes verified (pending-decisions.md:487 "MCP tools mapped to actions by an adapter component"; artcraft-suite.md:246, 251). But the central premise — "the adapter that reads it is a component, not a signer: nothing it declares is in a manifest" — is refuted by [mcp.md](/Users/btw/Documents/repos/dodos/contracts/mcp.md) at `origin/step0-contracts`: "An adapter is an ordinary component of the `service` world that exports `actions`, packaged and signed by its publisher. … Its manifest is drafted by a tool from `tools/list` (the mechanical part above), then completed and signed by a person (classes, items, hosts, refused tools)." And: "The effect class … is declared in the signed manifest by whoever packages the adapter, and that publisher answers for it. The hints only seed a proposal … A human checks each one." A tool the manifest does not name is not an action: `invoke` builds `tools/call` from the *action's* name, so a server-side `list_changed` renames or additions simply fail or are never offered. The ArtCraft gateway case is explicitly refused: point 5 of mcp.md — "A tool whose parameters are free text or any JSON (`command_run {id, params?}` …) … Not mapped. Alternative for a publisher who insists: class `irreversible`, so every call is confirmed with its raw JSON"; `craft_call_tool` is the same shape (free `arguments?`). Pixel-driving tools, sampling, elicitation: not mapped (points 6-7). Remote servers: "the adapter is an action of reach `external` to the server's host" — so the residual rug-pull is exactly P-036 (declared by the page, 178/316, pending P-036), not a new hole. The reviewer's step 4 ("the class the adapter writes into the matrix is the server's own claim") is therefore wrong for the current contracts; it would be right only if P-022 were answered against mcp.md's design, and P-022 is still only *Leaning* (pending-decisions.md:62, 481-493).

**External claims, verified at source today.** MCP specification 2025-06-18, server/tools: `tools/list` request exists; `notifications/tools/list_changed` ("servers that declared the `listChanged` capability SHOULD send a notification"); and verbatim: "For trust & safety and security, clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers." The site's latest version today is **2026-07-28** ("Version 2026-07-28 (latest)"), which carries the same MUST sentence and says the tools set "MAY change over time" — matching what mcp.md cites. Invariant Labs April 2025: the original post was not re-read (the reviewer said secondary); secondary sources today confirm the two demonstrations — the April 1, 2025 poisoned `add` tool in Cursor (hidden text reading `~/.cursor/mcp.json` and `~/.ssh/id_rsa` through a `sidenote` parameter) and the rug pull (a server changing a tool's description after approval; postmark-mcp changed code instead, May 26, 2025, official GitHub MCP server). Willison's MCP mix-and-match example verified ("one MCP mixed all three patterns in a single tool").

### Finding 10 — a capture right reads the trusted path. **Verdict: confirmed, with one correction.**

Quotes verified. **Correction:** "no mark follows" is wrong — 194 (the reviewer's own quote) says a capture takes the union of the marks of the surfaces it captures, and core.wit:88-89 implements it: the `capture` principal "carries the union of the marks of the surfaces it shows". So the photographed confirmation is inside a marked object, and any task that later reads that capture takes the mark. What is true, and unaddressed: nothing blanks system material in a captured frame. 13 and 92 claim indicators and confirmations are "out of reach of applications", but ui.md:68 ("Only the compositor sees the pixels of other surfaces") is about drawing; with the capture right (93, ui.md:134) the compositor hands the pixels over deliberately, and the capturing application is not running under a task — 102 says it may "use every capability it was granted" — so its own manifest network right carries the frame out with no matrix cell ever consulted. The adversary row at 102 does not consider the capture right. Confirmed as a break of the Aligned baseline at 13.

**Smallest rule.** Right in direction; the contract currently only stamps marks (core.wit:88-89), it does not blank system material, so the rule must be added to the page (and then to the compositor).

### Finding 11 — the recogniser on neither list; the blind user's check. **Verdict: partly right.**

Quotes verified. **First half — partly right.** The recogniser is genuinely on neither list: 131's trusted item is the audio service and input chain, which "give keys the origin `user`" (keys, not words); 135's bounded list names "the model and the inference engine", the wake-word detector and input engines, not the recogniser. That is a real omission (the recogniser is a local speech model, ui.md:126). But the consequence the reviewer draws — a loudspeaker's speech becomes a request with origin `user` and no mark — is already declared by the page: point 7 (322), P-048 (pending-decisions.md:804-814, recommendation *Firm*), scenario 10 (304: "From a loudspeaker of another device, the request runs with origin `user`"). The contract matches: actions.wit:86-90 gives `via: "spoken"` parts origin `user`, shown in the bar as heard; core.wit:376-377 "The system routes the following speech to the recogniser". So the new content of the first half is only the list omission; the attack's outcome is already listed as pending, not missing. The proposed `heard` mark goes beyond P-048 and would not make voice tasks impossible (it changes only the external-read cell), but it is a proposal on top of an already-pending point.

**Second half — confirmed as an unsettled case.** 216 claims the secure attention key "is the only check that also works for a screen-reader user, since any application with the playback right can imitate a sound" — the reason addresses sound, but for a blind user the check is delivered by the screen reader reading text (ui.md:124), and 305 shows that channel can carry imitated "System:" text from an application window. For 216's claim to hold, pressing the SAK must move the focus to the system-drawn view (ui.md:17: the compositor owns the focus) and the screen reader must follow focus to it — the page never states either. So: state the mechanism, or withdraw "works for a screen-reader user". The reviewer's rule (b) is one valid fix.

## N1-N5: what the attacker's angle should have found and did not

- **N1 — the hostile keyboard answers the confirmation.** 214 lets any key on a focused confirmation answer it; scenario 13 (security.md:307) and point 12 (327) declare that a device which types as a keyboard has origin `user` and is "Not stopped today"; 214's "never by synthetic input" holds only because input injection is a capability nobody holds by default (ui.md:109) — but a typing peripheral is accepted input. Combined, a USB device can answer a pending confirmation with one keystroke and send the confirmed external modification while the user is elsewhere. The walk-through lists the pieces separately and never combines them; this is the concrete attack on 215's "not answerable by accident".
- **N2 — "Automatic, can be undone" is not unconditional.** Row 203 and 224 promise the undo, but the contract's `undo` answers `conflict` "if a later write touched the same objects" and `unsupported` if not undoable (actions.wit:227-229). A task that runs several automatic reversible writes (finding 8's delete-20-notes) can make earlier undos fail; the page states the undo without the conflict caveat.
- **N3 — the enforcer of the whole matrix is unnamed.** Trusted-list item 8 (security.md:128): "The documents name no service and no process for it"; point 10 (325) recommends a task service (P-039, *Firm*) and the compositor would draw a confirmation "only from what that service hands it". Until P-039 is answered, "enforced by the system and not by the model" (103) rests on a component no document names — a cannot-be-built-as-written item the attacker angle should have raised, since an unbuilt enforcer is an unenforced matrix.
- **N4 — the screen-read marks rule lives only in the contract.** agent.wit:285-288 makes reading any surface's accessibility tree add `untrusted` (unless the owner is the system) and `private` always ("what the user's screen shows is the user's"); security.md's provenance rules (191-196) state the capture rule (194) but never the tree-read rule, and scenario 295 mentions only `untrusted`. This is what narrows finding 1 to the store-object path, and security.md should carry the rule itself.
- **N5 — notification-carried actions run under an unnamed task.** ui.md:142: "a notification carries actions and a priority class"; catalog.wit:82-87: activating a button with an action "invokes the action through the task, under the same rules as `task.invoke`"; ui.wit:56 checks "actions within the task scope" at update. But no document says which task a notification's action runs under or what marks that task starts with: the click is origin `user`, and the notification's app-origin text is not a request part, so it never marks anything. Two outcomes the text allows — the action runs under the pending agent task (inheriting its marks) or under a fresh unmarked task in which a hostile app's notification button runs every automatic cell. Unsettled case: actor = the shell presenting a third-party notification; state = the user activates the notification's action.

## Corrections to security.md, as exact text, in order of severity

Anchor lines are those of HEAD. Severity order: breaks D-036, breaks D-035's secret fields, breaks the Aligned trusted path, removes the page's own guard rails, then the rest.

**C1 — after security.md:187, and amending :189** (findings 1, 2, N4; breaks D-036). Add:

> - **What sets `private`.** A write in the user zone is stamped `private` at write time: the user zone is the user's private data, so a `user`-origin document carries `private` before it is read. Reading the accessibility tree of any surface adds `private` always, since what the user's screen shows is the user's.

And replace :189 with:

> - Passing an object from one action to the next without reading it adds no mark to the planner: only reading the object's content does. Binding an object as an argument of an action call adds its marks to the task, because the receiving action reads the object; the matrix decides on the union of the task's marks and the marks of the objects bound to the pending call.

**C2 — after the matrix, :206** (finding 3; breaks D-035's secret fields). Add:

> - **An action that receives a secret is confirmed whatever its class.** The confirmation names the receiving application first, shows the secret masked, and the journal writes it as null.
