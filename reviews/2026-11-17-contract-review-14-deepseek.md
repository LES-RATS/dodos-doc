# Fourteenth review of the contract, by DeepSeek: the changes of D-141

**Date:** 17 November 2026. **Scope:** the contract `architecture/kernel-interface.md` at commit `a0e5848`, against the same file at `a1dca23` — the diff `git diff a1dca23 a0e5848 -- architecture decisions plan`, 802 lines changed, plus the four changed lines of `architecture/kernel.md`, `architecture/security.md`, `decisions/README.md` and `plan/progress.md`. **Commission:** the brief `REVIEW-22-CONTRACT.md`.

**How it was read.** The whole contract at `a0e5848` was read end to end, and every changed run of lines of the diff was read in its place in that text. All line numbers below are those of `architecture/kernel-interface.md` at `a0e5848`; a quotation is verbatim from that file, and nothing is quoted that was not found there by reading. Technical reports and pull requests of the reference model were not read in this pass: this review attacks the sentences of the contract on their own, as the brief asks.

**What the diff changed.** Eight hundred and two changed lines, in seven groups: (1) the sender of a message is the writer of the ring it came on, with the whole receive check rewritten around it; (2) a grant freed only when the holder's use entry counts no leaf, counted only under the index the granting node recorded once *answered*; (3) the anchor is the only source of a remote frame's frame, rights and depth; (4) the `memory_control` added to the depth rule of D-103; (5) kept debug areas and crash headers read as untrusted data; (6) a long list of smaller rules and constants (`FENCE_NS` 30 ms, `IOMMU_WAIT_NS` 10 ms, `CONSOLE_TICK_NS` 1.5 ms, `memory_split` `busy` on a leaf count, the `Report` layout, the RMRR devices, the level-line claims, the memory orders of the rings, the slot read, the clock and the inter-core interrupts); (7) two sentences marked "to verify" and one new open point for four sources not opened.

**Shape of this report.** Findings first, each with the lines, the scenario step by step, the guarantee that breaks, a severity and the smallest correction. Doubts after them, marked as doubts. Then what was checked and found sound, item by item, and the hardware sentences, with what could not be opened. One table at the end.

## Finding 1 — a `Release` frees the use entry the granting node was going to count, so the count reads 0 and the grant is freed over a frame a failed unit may still reach

**Lines.** 917 (`Release by the holder`), against 914 (`The count says what the holder translates`) and 1079 (G6, "frees a use entry only at a count of 0"), with 396 (a unit that failed) and 393.

**The two sentences that cannot both hold.** Line 917: the holder "sends *X* a `Release` that names the grant and its serial, and frees its use entry once the message is in the ring". Line 1079, G6: the holder's gate "frees a use entry only at a count of 0, so the granting node frees a grant only on that count (D-141)". And line 917's own count test: "it then frees the entry only if the count of *Y*'s use entry at the use index the entry records, read as a revocation reads it, is 0, and otherwise leaves the entry as it is and traces the message (code 11)". Line 915 defines that read: the count is "counted only if that entry names *X*, this grant, its serial and *X*'s generation, and as 0 otherwise".

**The scenario, step by step.** A unit of node *Y* fails (line 393): *Y*'s holder "answers *failed* to every request it holds"; line 396 empties "every record whose invalidation the unit did not confirm ... with its counts kept: the map counts, leaf counts and use-entry counts of its leaves are never lowered, so the chunks stay their node's and are never given, destroyed as a block or retyped, and a frame another node granted stays pinned, until the machine restarts; the capability and the frame are removed as usual".

1. *X* granted a frame to *Y*; *Y* mapped it into an `iospace` of a device behind the failed unit, so *Y*'s use entry for the grant counts at least one leaf, for ever (line 396).
2. The record of the remote capability is emptied by the unit failure, so nothing under the root is *unmapping* any more; *Y*'s removal of the root remote capability now runs to its end (line 915 only forbids removing the root "while a record under it is unmapping").
3. *Y* sends the `Release` and, per line 917, frees its use entry "once the message is in the ring" — with a count of 1, which line 1079 forbids but line 917 does not test.
4. *X* consumes the `Release`, reads the use index the grant entry records, and finds an entry that no longer names *X*, this grant, its serial and *X*'s generation; line 915's rule makes that read "0 otherwise".
5. The count being 0, line 917 frees the grant entry and removes its anchor. The untyped capability that the frame came from no longer has that descendant, so `memory_give` and `memory_split` are no longer `busy` on it (line 881: "`busy` if the untyped capability has a descendant"), and G5's map count of the chunk is 0, because a grantee's leaves "are counted in its use entry (G6), so each count has one writer" (line 1077). The chunk is given and retyped in another node while the failed unit still translates it for a device.

**The guarantee that breaks.** Line 396's own promise for a failed unit — "a frame another node granted stays pinned ... until the machine restarts" (the pin is the live grant entry, since the use-entry count no longer pins anything once the entry is gone) — and with it G (2) (line 1063) and G6's "A chunk under a live grant is never given", which stops covering the chunk.

**A second defect in the same place.** The `otherwise` branch of line 917 is unreachable in every case, not only this one: *Y* frees the use entry before *X* can consume the `Release`, so *X*'s read always lands on an entry that no longer names the grant, and the trace of code 11 that D-141 added for a holder "that released while its tables still translated the frame" can never be written. The same holds for the crossing paragraph at the end of line 917, which reads "If the entry is *revoking* ... the entry is freed" without repeating the count test it says it applies ("the count read in the same way").

**Severity: high.** It needs a failed IOMMU unit to arise, but what it costs is memory a device can still write into, handed to another node, and it silently voids the D-141 release guard.

**Smallest correction.** In line 917, the use entry is kept, with its count, until *X* has freed the grant entry: *Y* sends the `Release` and leaves the entry naming the grant, and frees the entry only once its count is 0 and *X*'s grant entry is gone (the existing `release pending` bit can serve as *released*, or a second bit can), and *X* frees a *released* grant entry only on a count of 0 read while the entry still names the grant. Then a leaf kept by a failed unit keeps both the use entry and the grant entry in place until the machine restarts, which is what line 396 already promises. The cost stays at the release: one read of the entry, as today.

## Finding 2 — a revocation whose root came back removed with a count above 0 leaves the entry *revoking*, and the next `Revoke` is refused by the receive check, so the calling thread waits for ever

**Lines.** 915 (`Revocation`, the `RevokeStep` rule and "a removal on *Y* done for a `Revoke` frees *Y*'s use entry when it removes the root"), 966 (the receive check for a message that names a grant), 916 (the pinned grant, which is the only state that ends a removal without a message), 396.

**The scenario, step by step.** Same start as finding 1: *Y*'s unit failed with one of the grant's leaves under it, and *Y*'s use entry counts that leaf for ever.

1. A removal on *X* reaches the anchor. The grant is *answered*, so line 915 makes it *revoking* and sends *Y* a `Revoke` naming the grant, its serial and the use index; the calling thread of *X* waits in *waiting for another node*.
2. *Y* runs one removal step on the root remote capability. Nothing under the root is *unmapping* (line 396 emptied the records), so the root is removed, and per line 915 "a removal on *Y* done for a `Revoke` frees *Y*'s use entry when it removes the root, and sends no `Release`".
3. *Y* answers `RevokeStep` reporting the root removed. The order of *Y*'s freeing of the use entry and its writing of the answer into the ring is not stated. Both orders are legal:
   - If *Y* freed the entry first, *X* reads the count "as a revocation reads it" as 0 (line 915: "and as 0 otherwise"), frees the grant entry, and the removal completes — which is finding 1's fault, with the same consequence.
   - If *X*'s read lands between the write of the answer and the freeing, *X* reads a count above 0 and, per line 915, "otherwise leaves it *revoking* and is traced (code 11)"; "any other answer, and that one, makes the removal step return `again`, and its next call sends `Revoke` again".
4. The next `Revoke` reaches *Y*, whose receive check (line 966) requires that a message naming a grant match "the use entry naming the sender as granting node with that generation and serial (on the holder)". *Y*'s use entry is freed, so the check fails: the message "is consumed, and is traced (code 11)", and no answer is sent. Line 917's rule for a `Revoke` that finds the root already removed is written only for an entry whose flag *release pending* is set, which is not this state.
5. *X*'s removal step returns `again` again, sends `Revoke` again, and so on: the thread waits in *waiting for another node*, the removal never completes, the entry stays *revoking*, and one code-11 trace is written per round trip, for the life of the machine.

**The guarantee that breaks.** Not memory safety this time, but the liveness rule the contract states for its own waits: "So every wait of a kernel event is bounded by construction, whatever the cores do" (line 688), and the precedent the contract itself records for exactly this shape of bug ("the crossing left the revoking thread waiting for ever", line 917). Nothing here is a *pinned* grant; that is the only state the contract lets a removal skip (line 916).

**Severity: high for liveness, medium by likelihood.** It needs a failed unit *and* an unlucky interleaving, but the result is a thread that never wakes, a node whose memory is never reclaimed, and an unbounded trace.

**Smallest correction.** Two sentences. In line 915: a `Revoke` that names a grant whose use entry no longer names it is answered `RevokeStep` reporting the root removed (the holder no longer holds it), instead of being refused by the check of line 966 — the request was legitimate when it was sent, and the resource it names has already gone. And: a `RevokeStep` that reports the root removed with a count above 0 leaves the entry *pinned* (line 916's state) rather than *revoking*, traces it, and the removal step returns `busy` instead of `again`, so the call fails and no thread waits; a later removal returns `busy` at the same place until the machine restarts. This is the same shape as the answer the contract already gives for the failed unit: the memory is lost until the machine restarts, and the caller should be told so once.

## Finding 3 — the depth proof's last step and its figure of 191 do not follow from the counting before them

**Lines.** 123 (the "Why" of the depth rule), with 120 ("A capability at depth 64 can therefore still be moved, also by IPC; it can no longer be derived") and 864.

**What the proof says.** "Call *restricted* the `untyped` and `memory_control` capabilities and the roots of spaces; the others are *ordinary*. The walk goes from a capability to one derived from it (the depth grows by one), or from the root of a space to a capability the space holds. ... So while the walk is on restricted capabilities the depth never shrinks and stays equal at most once per level: at most 128 capabilities. Once the walk reaches an ordinary capability it stays on ordinary ones, because everything derived from an ordinary capability is a copy, the root of nothing, or an `irq` ...: at most 64 more. So no capability can depend on itself, and the walk is shorter than 192 capabilities (the longest one that can be built has 191)."

**The step that fails.** "At most 128" and "at most 64 more" are bounds taken on the same depth budget: the restricted walk spends a depth on each level it uses, and the ordinary walk grows the depth by one per step until the limit of 64. If the restricted walk ends at depth *d*, the ordinary walk has at most 64 − *d* steps, so the walk is at most 2(*d* + 1) + (64 − *d*) = *d* + 66, at most 130 at *d* = 64. The two maxima cannot be reached one after the other. Two consequences, both about sentences rather than about safety: `at most 192` does not give "shorter than 192", because a bound of 192 is not strict; and "the longest one that can be built has 191" describes a walk that the same paragraph's rules forbid, so nothing derives it.

**The guarantee that breaks.** None: the conclusion the paragraph exists for — the depth never shrinks on restricted capabilities, grows by one on every derivation, and holds at most twice per level, so no capability can depend on itself and the walk is bounded — is sound, including the new `memory_control` case (line 864: "**The `memory_control` is restricted by the depth rule as an `untyped` is (D-141)**"; a block taken through a copy at the copy's depth + 1 goes into a space deeper than the copy, so that space cannot hold the copy, which is exactly the cycle D-140 missed).

**Severity: low.** A number in a proof that nobody uses as a constant.

**Smallest correction.** Replace "at most 128 ... at most 64 more ... shorter than 192 (the longest one that can be built has 191)" by the shared-budget count: "at most two restricted capabilities per level, and the ordinary capabilities that follow grow the depth by one each, so the walk is at most 130 capabilities". If the figure 191 is needed somewhere, it must be derived, not asserted.

## Finding 4 — the range of `FENCE_NS` allows 12 ms, the value its own justification rejects as "less than two rounds"

**Lines.** 1505 (the row of the values table) and 1311 (the fence's rounds), with 1267 (when a node becomes unfenced).

**The row.** "| `FENCE_NS` | 30 ms | 12 ms to 1 s. Time for two rounds of the NMI grace, INIT and the two SIPIs after the delays of the SDM's example (11.2 ms each, as due events, D-141), and the stub; or for `CPU_OFF`. It was 10 ms, less than the SDM's example alone (the second round's verification by Hydrogen, section 3), then 20 ms, less than two rounds (D-141) |". Two rounds at 11.2 ms are 22.4 ms, so the reason given for 30 ms is that a value below 22.4 ms is too small — yet the range the machine may choose from starts at 12 ms, which is below two rounds and is exactly the mistake the paragraph says D-141 corrected when it moved 20 ms anyway (20 ms is *also* below 22.4 ms, which is why the default is 30 ms).

**The scenario.** A boot image declares `FENCE_NS` = 12 ms, inside the published range and inside `FENCE_RANGE_NS = (12_000_000, 1_000_000_000)` (line 1793), so the kernel accepts it: "the boot image states the times in `BootMembership`, and the kernel refuses values outside the ranges" (line 1496), and 12 ms is not outside. A core of a healthy node is caught in a firmware stall for 11.5 ms; the first round does not reach it and the second round does not finish before 12 ms have passed, so line 1267's rule fires — "`FENCE_NS` has passed since the first action of the fence without every confirmation" — and the node becomes *unfenced*, with all the consequences the contract attaches to that state.

**The guarantee that breaks.** The rule that a fence's timing leaves room for the mechanism the contract names, and the sentence "a slow but healthy node may be fenced" is a cost the owners accepted for `STALE_NS`, not something the range should allow to be built in for free.

**Severity: low.** No memory is lost; a healthy node is fenced, and the range lets an image do that on purpose.

**Smallest correction.** The range's lower bound becomes two rounds plus the stub, "23 ms to 1 s" for the 11.2 ms round of the reference machine, or the row states that the bound is measured per image as the start-up checks in line 688 do for `CORE_ANSWER_NS`.

## Finding 5 — the fence's "11.2 ms" does not match the delays it names, and 20.4 ms leaves 9.6 ms of the 30 ms unaccounted

**Lines.** 1311, and the same figure at 1505.

**The text.** Line 1311: "The delays follow the SDM's example, 10 ms after INIT and 200 µs between the two SIPIs ...; one round takes about 11.2 ms (`NMI_GRACE_NS`, 10 ms and 200 µs), and `FENCE_NS` (30 ms) covers two rounds and their stub (D-141)." The parenthetical names the round's components itself: 10 ms and 200 µs are 10.2 ms, not 11.2 ms. Either a third delay of 1 ms exists and is not named, or the round is 10.2 ms and the figure is wrong.

**Why it matters, and why it is not more severe.** With 11.2 ms the two rounds are 22.4 ms inside 30 ms; with 10.2 ms they are 20.4 ms inside 30 ms. Both fit, so the default is safe, and the 30 ms has 7.6 ms or 9.6 ms of headroom that is called "the stub", which is a page of code and cannot cost milliseconds. The number is what a later pass will compute the range from (finding 4), so it should be right where it is used.

**Severity: low.**

**Smallest correction.** Say "one round takes 10.2 ms (`NMI_GRACE_NS`, 10 ms and 200 µs; the SDM's example is an example, not a requirement)" and keep 30 ms, or name the delay that makes it 11.2 ms.

## Finding 6 — the first map of a received frame waits for an answer that a sealed or fenced granting node may never consume, and the stated bound is one ring period

**Lines.** 914 (the cost sentence at the end), 1249 and 1274 (a sealed node), 979 (what ends with a generation), 966.

**The sentence.** Line 914: the holder's gate counts a leaf only in the use entry "the grant entry records once the granting node has consumed the `SendAnswer` (*answered*): before that, `aspace_map` and `iospace_map` of the remote frame return `again` with nothing changed", and the cost: "a first map of a frame just received waits until its sender has consumed the answer, at most the latency of a kernel ring (one period of the recovery reserve under full load)".

**The scenario.** *Y* consumes the `Send` and writes the `SendAnswer` into the ring *Y* → *X*. *X* is then sealed for a replacement (line 1249: "Stopped cleanly, its block sealed, for a replacement only: it can be resumed with the same generation, on the same cores, within `SEAL_NS`"), which the contract allows to last up to a second and, if the seal is held longer, until evidence *seal* accuses it (line 1296). A sealed node "sends nothing new, but what it wrote before its seal is answered, and the answer waits in its ring until it resumes" (line 966): nothing consumes *Y*'s ring until *X* resumes. Every `aspace_map` and `iospace_map` of that frame returns `again` with nothing changed for the whole seal, and the caller cannot tell this from a ring that is merely busy. The same happens while *X* is *fenced* until R6 clears its entries, and while *X* is merely not scheduled under a full load, for more than one reserve period if the ring's consumer is behind.

**The guarantee that breaks.** Only the stated bound, not a safety property: the `again` is correct and the caller is expected to retry. But "at most the latency of a kernel ring (one period of the recovery reserve under full load)" is false, and the contract is otherwise careful to say when a wait is bounded by a seal (`SEAL_NS`) or by a generation's end.

**Severity: low.**

**Smallest correction.** Add the qualifier: "while the granting node is live and not sealed; a sealed granter consumes the answer when it resumes, and a fenced one ends the grant (R0, R2), which the map then reports as `gone`". One clause, at the same place.

## Doubts

These are marked as doubts because settling them needs a source or a measurement this pass did not open, or because the sentence is defensible but not derived.

1. **The `ARM64` user mask of a watchpoint is in `abi/`, which was not read.** Line 1667 rests the "no user breakpoint fires in the kernel" claim on two legs: on x86-64 the debug address registers compare linear addresses that "lie in the user range, so no access of the kernel matches"; on ARM64 "the user mask of a watchpoint's control gives it the privilege of EL0 only, and the kernel issues no unprivileged load or store (`LDTR`, `STTR` and their kin)". The second leg is exactly as strong as the mask that `abi/` publishes, and `abi/` was not read in this pass (the contract itself only says "a control word with a bit outside the architecture's user mask (in `abi/`) is `invalid`"). The first leg is sound as far as the contract's own description of the kernel goes, which I checked sentence by sentence: the message page is "mapped at the address *P* (0x1000 on the reference machine), read and write" in the user's space (line 2063) and reached by the kernel "through its own mapping of the frame" (line 1667); the two rings of a node pair are kept memory (line 967); `debug_write` takes "the first ⌈length / 8⌉ message words of the call" (line 1586); the register block of `thread_read_regs` travels in the caller's message page. I found no sentence in which the kernel touches a user address, including the ARM64 memory-operation exception 0x27 at line 459 ("the kernel restarts the copy or set"), which is an operation at the kernel's own level and so cannot match an EL0-only watchpoint either. **Doubt:** if `abi/`'s mask lets a user set the EL1 bit, the claim fails on ARM64 only, and the class 0x35 line at 459 should then read the other way.

2. **`CORE_ANSWER_NS` = 10 ms against 2 × *W* + *D* is consistent only for a small *H*.** Line 688 refuses a `CORE_ANSWER_NS` "not above the longest healthy wait ... 2 × *W* + *D*, with *W* = *N* × *H*", and line 1510 caps the value at 100 ms; with *N* = 64 and the hold *H* = 1 ms the eighth review used, the longest healthy wait is 128 ms plus *D* and no image with 64 cores could start. *H* is to be measured, so this is a doubt, not a finding: the three checks (`STALE_NS` above `CORE_ANSWER_NS` + *W*, `CORE_ANSWER_NS` above 2 × *W* + *D*, and the two ranges) are satisfiable together only if *H* is far below 1 ms once *N* is large. **Doubt:** whether the range of `CORE_ANSWER_NS` should widen with *N*, or the entry `Node` should refuse *N* whose 2 × *W* + *D* exceeds the range.

3. **`IOMMU_WAIT_NS` = 10 ms and `CORE_ANSWER_NS` = 10 ms have two different justifications for the same number.** Line 393: 10 ms, "below a stall of system management mode, which would have marked a healthy unit failed". Line 688: 10 ms, "above the longest firmware stall of a core". Both are arguments about firmware stalls, one requiring the bound to be *above* and the other *below* the stall. **Doubt:** if both numbers are provisional and equal by coincidence, nothing is wrong; if one of them is the same measurement used twice with the inequality reversed, one of the two is wrong.

4. **"A chunk under a live grant is never given" names no check, and the mechanism I found for it should be written down.** My reading is item 3 of the sound list: the anchor is a child of the frame capability, retyped objects are children of the untyped capability, and `memory_give` and `memory_split` are `busy` on a descendant. The contract never says in one sentence that the objects a retype makes are children of the *capability* in the derivation list — it says it for a block ("A block's capability is a child of the `memory_control` capability through which it was taken", line 864) and leaves it to the walk at line 123 for the rest. **Doubt:** if the objects a retype makes hang from the untyped *object* rather than from the capability, the descendant check does not see the anchor and the guarantee has no check at all; one sentence at G6 saying which check enforces "never given" would settle it either way.

## What was checked and found sound

1. **The sender is the ring's writer (attack 1).** G (1) now says it plainly: "the rings whose sender is *X* ... so each ring has one writer, its sender, and the consumer indices of the rings into *X* lie in *X*'s node beacon, which *X* alone writes: the receive check of every message rests on it, for the kernel rings both ways, the user rings and the rings a unit holder serves (D-141)" (line 1063), and the check is "**the sender the header names is the node whose ring the message was read from**" (line 966). I walked the paths the brief lists: both kernel rings of a pair, the user rings, answers (`RevokeStep`, `UnitAnswer`, `Report`, `SendAnswer`), `Handed` (which names the role's holder and target, and the role word's epoch), the unit service table (indexed by the peer the ring names, not by the header), a resume after a seal (a sealed node's earlier messages are answered when it resumes, and its ring is the only place the sender can be read), and a node restarted in the same slot: the header's generation against the member word refuses the old generation's messages, the receiver's own generation refuses messages to the old generation, and the consumer index that a fresh start resets makes the stale entries be consumed and traced rather than delivered. I found no path where a message on a ring can be read as coming from a node other than the ring's writer, and none where an honest message of a live sender is refused: the ring's writer is the sender by construction, so the first check cannot fail for an honest pair.
2. **A grant's frame, rights and depth come from the anchor (attack 3).** Line 912 has the granting node's gate write the anchor "only for a frame whose chunks the ownership table gives to *X* with its generation, or that lies in *X*'s floor, in a device entry *X* owns or in the global read-only set (a kept frame, which every node may map read-only anyway: item 3 of (G))", and it closes the two doors I looked for: "A capability that is not a frame of the caller's own node, a remote frame capability included, cannot be listed (`invalid`)" — so a grant of a grant is impossible, and the chain "only the owner of a frame grants it" holds — and the depth: a capability at depth 64 is `invalid` in `node_send` "whose anchor would be deeper than the tree allows" (line 1002), while the receiver accepts an anchor of depth 1 to 64, which is the same rule seen from the other side, since the anchor is the frame's child. The read-only-set exception is safe on all three of the brief's counts: rights (the set is read and execute, item 3 of (G), and G3 refuses a writable leaf there: "global read-only pages are never writable"), revocation (a kept frame is in no untyped and has no owner to revoke it, and freeing the grant removes the anchor only), and lifetime (the set is kept for the boot). Its cost is where the contract puts it: "the reads of G3 (2), at most *E* chunks per frame, paid at a `node_send` that grants".
3. **A chunk under a live grant is never given, and I could find the mechanism the sentence relies on without stating it.** Line 915 and G6 both assert it, and G5's conditions (map count 0) do not see a grantee's leaves, which G4 counts in the use entry "so each count has one writer". The mechanism is the derivation tree: the anchor is "a new child of the frame capability in *X*'s derivation list" (line 912), the frame capability is a descendant of the untyped it was retyped from, and both `memory_give` and `memory_split` are `busy` when the untyped has a descendant (line 881: "`busy` if the untyped capability has a descendant, then `busy` if a piece of it lives"; line 886: "`busy` if the untyped has a descendant or if a piece lives"). So the anchor keeps the give and the split away while the grant lives, and a removal of the untyped reaches the anchor first and waits on the revocation. **A note, not a finding:** the rule is stated as a guarantee and enforced by a check three sections away, and neither of the two sentences that state it names the descendant rule; a reader of G6 alone would look for a per-chunk grant count that does not exist.
4. **The use entry the grant records is the one that ties the count to the leaves (attack 2, the part that holds).** A faulty holder cannot choose the entry its gate counts in (line 914: "the use index comes from the holder's answer, so a holder's kernel could count its leaves in a second use entry naming the grant, or answer another index, and the count the granting node read would be 0 under live translations; only an index the granting node recorded before the first leaf ties the count to the leaves"), the write order of the count and the grant entry is set on both sides with the compare-and-swap and read semantics per architecture (Arm DDI 0487 B2.3.7 quoted, RISC-V `amocas.aqrl` or LR/SC plus a fence), a `Send` that finds the use table full delivers nothing ("B's open case does not arise", line 2280), and a frame reported not delivered had no answered entry to count under. Aside from findings 1 and 2, I walked the brief's list — `Send`, `SendAnswer`, map, `Release`, `Revoke`, `RevokeStep`, the death of either node, a seal — and found the outcomes the table at lines 925-929 states, including the two restrictions the D-131 crossings needed (a `Release` crossing a `Revoke` acts once, in either order; a `Revoke` that meets a pending release finds the root removed).
5. **`memory_control` under the depth rule (attack 4).** The amended proof at line 123 is sound for the reason given in finding 3: the only place where the depth stays equal is "from the root of a space to an `untyped` or a `memory_control` it holds", and the next move from either is a derivation; a block taken through a copy at depth *d* is at *d* + 1 and can only be placed in a space deeper than the copy, which is why the D-140 cycle (memory_control, block, space root, memory_control) is gone (line 864). I looked for another cycle of the same shape through every kind that is not a plain copy: `irq_control` (its `irq`s "hold nothing", so a walk that reaches one ends in copies), `ioports` (a child narrows its range and derives nothing), `iommu`, `task`, `thread`, `node`, `role`, `sched`, `notify`, `endpoint`, `reply`, `debug`, `cspace`, `aspace`, `iospace`, `vcpu` (reserved), and `frame` (its anchor is a child in the granter's list, which grows the depth by one and can be granted no deeper than 63). I found no second cycle and no unbounded removal walk.
6. **A debug area and a crash header are a faulty kernel's data (attack 5).** Line 1553 continues an area only "if the header's magic and version are right and each of its two next sequences is at least 1, below 2^63 and agrees with its ring", otherwise clears it, starts at 1 and writes one code 12 entry, and adds "It reads nothing else from the area". A next sequence of 0 or of 2^64 − 1 can no longer leave the next generation without an index or without room, the reader's loop is bounded by `N` (line 1551), and line 1613 has the sentence the rest of the section rests on: "A record from a kernel that went wrong may hold anything: it is data, never trusted." The console's new rule names a node "by the core word of the area's core, never by the area header", which is the only field a faulty writer cannot choose. The crash area's "header of sequence 2^64 − 1 is not valid" is consistent with the same argument.
7. **The cost rule of D-117 (attack 6, the principle).** Every new check I could find is paid at a rare event: the anchor reads at a `node_send` that grants (line 912), the use entry at a release or a `RevokeStep` (line 914), the two extra fields of the grant entry at a map (line 914), the free-entry check of the answer at a message received, the debug area's two sequence reads at a core's start (line 1553), the console's pacing at a due event (line 1654). The one place where the diff claims a bound rather than a cost — the first map's wait (finding 6) — is the one that is not bounded as stated. Nothing in the diff adds work to an ordinary memory access or a TLB miss.
8. **The constants, each sum checked against its own sentence.** The console: `CONSOLE_TICK_NS` 1.5 ms, "16 bytes leave in 1.39 ms" at 115,200 baud and ten bits a byte — 16 × 10 / 115,200 = 1.389 ms, which is inside 1.5 ms, and the check "if the transmit status reads empty" is what makes the next write wait for the whole tick, so the rate is the tick's and not the byte's. `IOMMU_WAIT_NS` 10 ms is read at each step of the holder's recovery reserve and the completion is read before the time (line 393), so a delayed reserve cannot fail a healthy unit that has finished. `STALE_NS`, `STUCK_NS`, `SWEEP_NS` are above the waits they must cover (line 1502's start-up refusal of a `STALE_NS` "not above `CORE_ANSWER_NS` + *W*"), and the letter *W* for the longest kernel event is used consistently where the diff replaced *E* by it (line 688 and the four checks). The node beacon's new size (1.1 MB, line 1930) was not recomputed in this pass. The remaining two constant problems are findings 4 and 5.
9. **The ARM64 trap classes at the kernel's own level (line 459).** 0x21, 0x25, 0x31, 0x33 and 0x35 are the "current EL" forms of instruction abort, data abort, breakpoint, software step and watchpoint, so treating them as kernel bugs is the right reading and is consistent with line 1667. I did not open DDI 0487 in this pass: this check is against the shape of the encoding as I know it, and the sentence rests on the source, not on this review.

## The other four files of the diff

`architecture/kernel.md` and `security.md` change four lines between them, and both are consistent with the contract: containment now takes the sender "from the ring the message came on (D-141)", and the formal models add RVWMO. The security page's row for a faulty kernel of one node gains a "**Bounded since D-141:**" clause with two parts, the identity — which the ring gives — and "the frames granted to it, which the granting node frees only on the count of the use entry the faulty node's own gate wrote, so it cannot have a frame it still translates freed". That second part is true as long as the count is readable when the granting node reads it, which is exactly what finding 1 breaks at a `Release`: the holder frees the entry, so the node that "wrote" the count is no longer readable and the freeing goes through the "as 0 otherwise" path. The security page inherits finding 1 and needs the same correction.

`decisions/README.md` carries the D-141 row and four amendments. The D-141 row states the rule that finding 1 contradicts, in the same words as G6: "the holder's gate therefore counts a leaf under a grant only in the use entry the grant entry records once *answered* ... and frees a use entry only at a count of 0". So the contradiction is not only inside the contract: the text at line 917 disagrees with the decision that commissioned it. The D-103 amendment ("the `memory_control` is restricted as an `untyped` is ... the bound of the walk (191) is unchanged") carries finding 3's figure, and the D-120 amendment ("the granting node's gate writes an anchor only over memory its node holds, and the holder maps the anchor's frame, never the `Send`'s") is the sentence the contract now implements at line 912 and 914. `plan/progress.md` changes are status only.
