## Verdict

Pass 13 closes cross-generation grant-slot confusion and single-crash reclaim barriers on static three-node topologies, yet out-of-order message races, missing request/serial checks, and eager `placed` updates still break cross-node isolation, strand waiters and moved capabilities, and allow a fenced/dead node's core to keep running. Specifically, stale `Body::RevokeStep`, `Body::Move`, and `Body::Request` packets mutate newly issued objects or free newly mapped physical grants, while `core_place`, `Sealed`-to-`Resume`, `unlink`, and `thread_move` violate explicit contract guarantees. Finally, `liveness.rs` and `way_out` exercise only static three-core single-fault runs and leave `Starting`, `Revoking`, `Host`/`Retire`/`SelfReported`, co-hosted `CorePlace`, `thread_move` crashes, and leaked `Wait::Node` / `Request` states unverified.

## Findings

### F1 — Stale `RevokeStep` / `Revoke` under concurrent `Release` and slot reuse frees live mapped grants and permanently hangs waiters (`Model`; minor `Contract` ambiguity)

- **What is wrong:** `Request::Revoke { thread, grant }` records neither `serial` nor `grantee`, `Body::RevokeStep { id, done }` omits `(grant, serial)`, and `asked(id)` only checks `grants[grant].is_none_or(|e| e.grantee == from && e.generation == generation)`. Combined with `released()` freeing a `GrantState::Revoking` grant without updating `Request::Revoke`:
  1. **Isolation breach (`run`):** If Node 0 calls `CapRevoke` on a mapped grant `(0, 0)` to Node 1, Node 1 deletes its remote cap (`Body::Release(0, 0)`), `Body::Revoke` arrives at Node 1 (queuing `RevokeStep(id, true)`), `Release(0, 0)` frees grant `0` (`serial` becomes `1`), Node 0 grants a *new* frame `F2` on `(0, serial=1)` to Node 1 and Node 1 maps `F2`, and then stale `RevokeStep(id, true)` arrives: `asked(id)` passes (`grantee == 1`) and `revoked_step()` calls `free_grant(0)`, freeing the **live mapped grant `(0, 1)`** while Node 1 still translates `F2` (`sys.check()` fails invariant 71).
  2. **Stuck waiter via third-node reuse (`run`):** Same race, except `(0, 1)` is granted to Node 2: stale `RevokeStep(id, true)` fails `e.grantee == from` (`2 != 1`), is traced `Refused`, and the caller stays in `Wait::Node` forever.
  3. **Stuck waiter via late `Body::Revoke` (`run`):** Same race, except `Release(0, 0)` reaches Node 0 and `(0, 1)` is delivered to Node 1 *before* `Body::Revoke(id, 0, 0)` reaches Node 1: `misdirected` sees `!granter(0, 0)` and `remotes.any(node == 0 && grant == 0)` is true (`serial == 1`), so `Body::Revoke` is refused (`Refused`), no `RevokeStep` is ever sent, and the caller stays in `Wait::Node` forever.
  4. **False refusal trace on concurrent unmapped release (`run`):** If Node 1 drops an unmapped remote cap (`Body::Release`) concurrently with synchronous `revoke_anchor` (`free_grant`), the legitimate `Body::Release` is traced as `TraceCode::Refused`. The contract (`Who may send what`, line 855) states that a release with the wrong serial/grantee is refused and traced, without distinguishing a benign concurrent free of the sender's prior `(grant, serial)`.
- **Where:** `model/src/remote.rs:606-615, 622-630, 1192-1204, 1324-1374`; `Docs/architecture/kernel-interface.md:842-844, 855`.
- **How known (`run`):** `adversarial_review7.rs`: `f1b_revoke_step_race_frees_new_live_mapped_grant_on_same_peer`, `f1a_revoke_step_race_sticks_waiter_forever_when_slot_reused_for_third_node`, `f1c_late_revoke_after_same_peer_slot_reuse_is_refused_and_sticks_waiter`, and `f1d_concurrent_release_after_sync_revoke_emits_refused_trace` (all pass).
- **What a kernel author would do wrong:** Trust `Request::Revoke` by `id` alone without carrying `(grant, serial)` in `Body::RevokeStep` or clearing/completing pending `Request::Revoke` when `Release` frees `(grant, serial)`, leading to cross-node use-after-free of physical frames or permanent revocation deadlocks.
- **Smallest correction:** Store `(grantee, grant, serial)` in `Request::Revoke`; carry `(grant, serial)` in `Body::RevokeStep`; in `released()`, complete any matching `Request::Revoke { grant, serial }` with `Again`; in `misdirected()`/`revoked_step()`, accept `RevokeStep` matching `(grant, serial)` and silently ignore already-freed serials instead of freeing reused slots; and allow `Body::Revoke` whose `(grant, serial)` is absent in `granter` to answer `RevokeStep { id, grant, serial, done: true }` even if `grant` now holds a newer `serial`.

### F2 — `core_place` + `core_stop` fences the wrong physical core and leaves a `Dead` node running; `CORE_STOP_RETIRE` retires a live core (`Contract & Model`)

- **What is wrong:**
  1. **Fence targets the wrong core (`run`):** Contract (`kernel-interface.md:1194`) says `core_place` binds `placed[node] = physical` immediately and *"a live node moves at its next event boundary"*. `core_place` (`recovery.rs:401`) sets `self.table.placed[node] = physical` immediately, while `begin_fence` / `fence_unit` (`recovery.rs:662, 680`) NMI/INIT `self.table.placed[node]`. Calling `core_place(1, 2)` followed by `core_stop(1, CORE_STOP_KILL)` before Node 1 migrates fences physical Core 2 (host-killing innocent Node 2 with `Evidence::Host`) and declares Node 1 `Fenced` then `Dead`, while **`self.cores[1]` remains `CoreState::Running`**. Even `System::check()` invariant 84 passes because it inspects `placed[node]` (`2`) rather than the physical core actually running Node 1 (`1`).
  2. **Live core marked unusable (`run`):** When `core_stop(parked_node, CORE_STOP_RETIRE)` stops a `Sealed` (or `parked_block`) node placed on Core 2 while Node 2 runs actively on Core 2 (`stops_core == false`), `recovery.rs:247-250` unconditionally sets `self.table.unusable[core_of] = true`, retiring Core 2 while Node 2 is still `Live` and `Running` on it (contract line 1182 says *"the physical core that runs the node"*).
- **Where:** `Docs/architecture/kernel-interface.md:1182, 1194`; `model/src/recovery.rs:220-221, 247-250, 359-403, 662, 680`; `model/src/system.rs:708-720`.
- **How known (`run`):** `adversarial_review7.rs`: `f2_core_place_then_core_stop_fences_wrong_core_and_retire_on_parked_breaks_live_core` (passes).
- **What a kernel author would do wrong:** Fence only the newly requested `placed[node]` slot while a migrating `Live` node is still executing on its old physical core (breaking containment after `Dead`), or set a live shared core `unusable` when retiring a parked/sealed node on it.
- **Smallest correction:** On a `Live` node, defer updating the fence-target placement (`running_core` vs `target_core`) until the node parks off its old core so `core_stop` always fences the core that actually holds the node's live execution (or waits for migration); and gate `unusable[core_of] = true` on `stops_core` (or return `Busy` for `CORE_STOP_RETIRE` on a co-hosted parked/sealed node).

### F3 — `Body::Move` and `Body::Request` omit grant `serial` (and `Body::Request` bypasses `misdirected`); `place_transfer` omits granter `Live`/serial validation (`Model`)

- **What is wrong:** Three protocol messages act on grants without verifying `(grant, serial)` in `misdirected()` or handlers:
  1. **`Body::Move` (`run`):** `remote.rs:640-646` checks `grants[thread]` and `grants[sched]` for `grantee == from && generation == generation`, with no `serial`. Because `ThreadMove` does not freeze the caller's remote caps to `destination`/`sched`, the caller can delete them (`Body::Release`), let the peer reuse grant slots `0`/`1` for a different `(threadB, schedB)` to the same node, and deliver the stale `Body::Move`, overwriting and configuring `(threadB, schedB)`.
  2. **`Body::Request` (`run`):** `forward()` (`remote.rs:414`) rewrites remote capability slots into `SlotAddr::own(anchor_index(grant))` with no `serial`, and `Body::Request` is completely exempt from `misdirected()` (`remote.rs:658`). If Node 0 calls `Signal(remote_notifyA)` (grant `0, serial 0`), deletes its remote cap (`Release`), Node 1 reuses slot `0` (`serial 1`) for `notifyB` granted to **Node 2**, and the stale `Body::Request` arrives, Node 1 signals **Node 2's** `notifyB`.
  3. **`Body::TransferGrant` (`run`):** `place_transfer()` (`remote.rs:990`) validates `Crossing::Home` grants as `Live` with matching `serial`, but does **not** check `table.grants[from][grant]` for `Crossing::Grant`. If the sender synchronously revokes the grant (`CapRevoke(parent)`) while `TransferGrant` is in flight, the receiver still installs a dead `Remote` cap and `UseEntry` and delivers `caps == 1` without `FLAG_CAPS_DROPPED`.
- **Where:** `model/src/remote.rs:414, 535, 585-664, 990`; `model/src/moves.rs:107-113`.
- **How known (`run`):** `adversarial_review7.rs`: `f5a_stale_body_move_without_serial_overwrites_reused_grant_thread_and_sched`, `f5b_stale_body_request_without_serial_hits_third_node_reused_notify`, and `f5c_transfer_grant_installs_stale_remote_after_granter_sync_revoked` (all pass).
- **What a kernel author would do wrong:** Assume `anchor_index(grant)` and `(from, generation)` uniquely name a grant across its slot's lifetime, enabling cross-object signaling/corruption when grant slots are reused within one generation.
- **Smallest correction:** Carry `(grant, serial)` in `Body::Move` and in rewritten capability arguments of `Body::Request`, validate `grantee(grant, serial)` in `misdirected()`/`serve_request()`, and check `grants[from][grant].state == Live && .serial == serial` in `place_transfer()` before accepting `Crossing::Grant`.

### F4 — `Sealed` → `Resume` and co-hosted sealing/resume drop R0/R3/save-seal cleanup, leaving stuck moves, `Live` grants to dead nodes, false `Host` kills, and 2-node sealing deadlocks (`Model`, plus `Contract` gaps)

- **What is wrong:**
  1. **Resumed node skips R0 `isolate()` and R3/cleanup (`run`):** `sealing_unit()` drains `proxies` (`roles.rs:493-505`) but leaves outbound `requests`, `held_requests`, `outstanding`, and `GrantState::Live` entries untouched. When peer `P` dies while Node 0 is `Sealed`, Node 0's `maps_of[P]` is `false` (unless Node 0 mapped `P`), and on `CORE_START_RESUME` (`recovery.rs:1176`), `started(true)` only calls `drop_stale_remotes()` (R2), **never `isolate(P)`**. Further, `unpin()` (`recovery.rs:1093`) only frees `GrantState::Pinned`, never `GrantState::Live` or `Revoking`. Thus outbound `Request::Move` keeps `Wait::Node` and `in_move` (`CapDelete` → `Error::Again`) stuck forever, `outstanding[P]` leaks, and `GrantState::Live` entries to dead `P` stay unfreed forever.
  2. **Co-hosted `CORE_START_RESUME` clears `save_seal` without setting evicted node's `save_seal` (`run`):** `core_start(RESUME)` (`recovery.rs:151-155`) allows resuming a `Sealed` node onto a core running another node `Z`. `System::start_node` (`system.rs:426-441`) updates `core_beacons[core].running = node` without setting `beacons[Z].save_seal = true`. When `node` is subsequently killed, `fenced()` (`recovery.rs:793`) sees `save_seal == false` on `Z` and **falsely kills `Z` with `Evidence::Host`**.
  3. **2-node `Sealing` deadlock on last `Live` node crash (`run`):** If Node 0 is `Sealing` (`Handing(0 -> 1)`) and the sole `Live` node `1` hangs, `recovery_unit()` (`recovery.rs:595`) checks `self.live_nodes().any(|z| z != 1)` (`false`, since `0` is `Sealing`), refusing to accuse `1`; meanwhile `sealing_unit()` cannot complete (`named == true`), deadlocking the machine.
  4. **Additional gaps (`read`):**
     - Host-sealing in `fenced()` (`recovery.rs:793-795`) transitions a co-hosted `Starting`/`Live` node straight to `Sealed` without running `sealing_unit()`, leaving its active `proxies` unanswered until resume or kill.
     - `sealing_unit()` does not check/refuse an already-queued inbound `Body::Move` in flight when transitioning to `Sealed`, stranding the mover in `Wait::Node`/`Again` until resume or kill.
     - `evidence()` (`recovery.rs:437-446`) checks `stale` (`stale_ns` = 10 ms) without excluding `MemberState::Starting`, so a `Starting` node stalls out at `stale_ns` instead of `START_NS` (1 s).
- **Where:** `Docs/architecture/kernel-interface.md:1137-1138, 1175, 1181-1184, 1213`; `model/src/recovery.rs:151-155, 437-446, 595, 793-805, 1089-1106, 1167-1191`; `model/src/roles.rs:464-534`; `model/src/system.rs:423-441`.
- **How known (`run` + `read`):** `run` via `adversarial_review7.rs`: `f3_sealed_resume_skips_isolate_stranding_move_and_live_grants`, `f3b_cohosted_resume_forgets_save_seal_causing_false_host_kill`, and `sealing_node_deadlocks_two_node_system_when_last_live_node_hangs` (all pass); `read` for host-seal `proxies`, in-flight `Body::Move` vs `Seal`, and `Starting` vs `stale_ns`.
- **What a kernel author would do wrong:** Run only R2 on `RESUME`, forget to save the evicted co-hosted node's seal before switching `core_beacon.running`, or omit a contract rule for a sealing node whose last live peer dies.
- **Smallest correction:** In `started(true)`, call `isolate(p)` for every peer whose generation ended (`Dead` or `generation != recorded`) and let `unpin()` also free `GrantState::Live`/`Revoking` entries when `grantee_over`; set `beacons[prev_running].save_seal = true` when switching a running core in `start_node(RESUME)` (and in `fenced()` host-sealing, drain/reset `proxies` or refuse co-hosted live nodes without sealed state); add `!matches!(member.state(), MemberState::Starting)` to `stale` in `evidence()`; and specify in the contract whether a sealing node aborts sealing back to `Live` or keeps running if no other live node remains.

### F5 — `unlink()` breaks no-wait completion on thread destruction; `asked(id)` returns `true` for `None` and ignores request kind; out-of-bounds role panics (`Model`)

- **What is wrong:**
  1. **`Send` with caps and `UnitRequest` dropped on thread destruction (`run`):** Contract line 854 requires *"A request that holds no wait there completes without the thread, so nothing is left half done"*. Yet `unlink()` (`ipc.rs:707-710`) falls into `_ => { self.cancel_remote(id); self.requests.remove(&id); }` for both `Request::Call` and `Request::Unit`:
     - When a thread destroys itself/is deleted *after* `Send` with capabilities delivered words (`Body::TransferAsk` in flight, `waits == false`), `cancel_remote` returns `None`, `unlink` removes `Request::Call`, and `grant_transfer()` (`remote.rs:855`) returns `grants: None`, falsely delivering `FLAG_CAPS_DROPPED` to the receiver.
     - When an `IoSpaceAttach` thread is destroyed while `Request::Unit` is in flight during a role hand-over, `unlink` deletes `Request::Unit`, dropping epoch retries (`answered_unit(..., false)`).
  2. **Spurious/mismatched `Body::Answer` bypasses `misdirected`, corrupts `outstanding`, and panics `serve_request` (`run`):** Because `unlink` removed `Request::Call` early, `asked(id)` (`remote.rs:607`) returns `None => true` and does not match the `Request` variant against the `Body` variant. A single spurious `Body::Answer { id: 999_999, .. }` bypasses `misdirected` (zero `Refused` trace!), decrements `outstanding[from]`, and causes the 17th concurrent request to panic `serve_request()` (`remote.rs:679`: `"the calling node counts its requests"`). Similarly (`read`), `answered_request()` calls `self.requests.remove(&id)` before matching `Request::Call`, so a mismatched `Body::Answer` deletes an active `Request::Move`/`Revoke`/`Transfer`/`Unit`.
  3. **Unchecked role index panic (`run`):** `Body::Handed { role }` (`remote.rs:650`) and `serve_unit` (`roles.rs:264`) index `self.table.roles[role]` without bounds checking, panicking on any out-of-range `role`.
- **Where:** `Docs/architecture/kernel-interface.md:854-855`; `model/src/ipc.rs:693-711`; `model/src/remote.rs:606-616, 650, 676-680, 733-758, 855`; `model/src/roles.rs:264`.
- **How known (`run` + `read`):** `adversarial_review7.rs::f4_destroyed_thread_no_wait_request_breaks_send_caps_and_unit_retry` (passes); `system::review7_unit_tests::unknown_answer_corrupts_outstanding_and_panics_serve_request_and_oob_role_panics` (passes, catching `remote.rs:679` and `remote.rs:650` panics); `read` for `answered_request()` removing non-`Call` requests.
- **What a kernel author would do wrong:** Treat `Wait::Node` destruction identically for waiting and non-waiting requests, or skip per-variant validation in `misdirected` (`None => true`), exposing `outstanding`/proxy accounting and `requests` to silent desynchronization or panics.
- **Smallest correction:** Make `Request::Call.thread` optional (`Option<ObjId>`), clear `thread = None` in `unlink()` without removing `Request::Call` or `Request::Unit` until `answered_request`/`grant_transfer`/`answered_unit` finishes (sending `Body::Cancel` only when `waits`), remove `None => true` from `asked(id)` while verifying the `Request` variant matches the `Body` variant, and bounds-check `role < self.table.roles.len()`.

### F6 — `Send` `Answer` vs `Refused` race loses moved capabilities in `kernel_space`, and all-or-nothing `Refused`/`Returned` checks strand remaining grants (`Model`; minor `Contract` gap)

- **What is wrong:**
  1. **`Answer` before `Refused` strands `Transfer::Move` capability (`run`):** When `place_transfer()` refuses a transfer of `Transfer::Move(slot)`, it sends `Body::Refused` and `Body::Answer(Sent { flags: FLAG_CAPS_DROPPED })` as separate messages. If `Answer` arrives first, `slot` looks empty to user space; if user space places a new capability in `slot` before `Body::Refused` arrives, `refused()` (`remote.rs:1229`) frees `grant`, hits `Some(_) => {}`, and leaves the moved capability permanently stranded in `kernel_space`'s `anchor(grant)` (irreversible loss of user space's last capability to that object, undetected by `System::check()`).
  2. **All-or-nothing `Refused`/`Returned` check leaks remaining grants (`run`):** In `misdirected()` (`remote.rs:632-639`), `Body::Refused { grants }` and `Body::Returned { grants }` verify `grants.iter().all(...)`. In a multi-capability transfer `[Move(A), Move(B)]`, if `A` is revoked/freed before `Body::Refused` arrives, `all()` fails and rejects the entire `Body::Refused` as `Refused`, stranding `B` in `anchor(1)` with `GrantState::Live` forever (and analogously stranding remaining `Home`-moved remote caps for `Body::Returned`).
- **Where:** `model/src/remote.rs:632-639, 1075-1112, 1208-1252`.
- **How known (`run`):** `adversarial_review7.rs`: `f7_send_move_answer_before_refused_race_strands_cap_after_slot_refill` and `f6_multi_grant_refused_partial_revocation_strands_second_moved_cap` (both pass).
- **What a kernel author would do wrong:** Report `Send` completion before refused moved capabilities are restored (or before slot reuse is prevented), or reject a whole batch of `Refused`/`Returned` grants because one grant was concurrently released/revoked.
- **Smallest correction:** Wait to send `Body::Answer(FLAG_CAPS_DROPPED)` until `Refused` restoration finishes (or return refused `Moved` grants on the `Answer`/keep the sender's slot marked reserved until `Refused` arrives), and check each `(grant, serial)` individually inside `refused()`/`returned()` instead of rejecting the entire batch in `misdirected()`.

### F7 — Missing cross-node `cap_derive` / `cap_move` / `untyped_retype` grants and missing remote checks on secondary arguments cause panics (`Model`)

- **What is wrong:**
  1. **Cross-node `via` CSpace panics (`run`):** Contract line 836 explicitly requires `cap_derive`, `cap_move`, and `untyped_retype` with a destination slot in a remote node's `CSpace` to create a grant (waiting in `Wait::Node`). None of those calls appear in `capability_arguments()` (`remote.rs:246-270`), so `destination()` (`lib.rs:1635`) resolves `through()` to the remote `CSpace` `ObjId` and **panics** in `self.cspaces[&space]` (`no entry found for key`). (`CSpaceGrow`, `SchedConfigure`, `SchedSetCores`, `SchedCount`, `ASpaceProtect`, `ASpaceUnmap`, `ReplyRecv`, `IoSpace*` are likewise omitted from `capability_arguments()`.)
  2. **Remote secondary capabilities on local objects panic (`run`):** Contract line 851 says a call executed by one node rejects capabilities naming objects of another node with `Error::Invalid` (if not remote parameters of a forwarded call). Calling `SchedBind` on a local `sched` with a remote `thread` passes `self.object(...)` and **panics** in `live(&mut self.threads, thread)` (`sched.rs:620`, `no entry found for key`). By inspection (`read`), `TaskAttach`, `NotifyBind`, `ThreadConfigure`, `TimerSet`, and `IrqBind` have the same unguarded lookup pattern.
- **Where:** `Docs/architecture/kernel-interface.md:836, 851`; `model/src/remote.rs:246-270`; `model/src/lib.rs:1530-1536, 1633-1638`; `model/src/caps.rs:181, 217, 285`; `model/src/sched.rs:620`.
- **How known (`run` + `read`):** `adversarial_review7.rs::f8_cross_node_cspace_via_and_secondary_remote_caps_panic` (passes, catching both `lib.rs:1635` and `sched.rs:620` panics); `read` for the other omitted calls and local secondary capability lookups.
- **What a kernel author would do wrong:** Either crash the kernel assuming every `CSpace`/`Thread`/`Task`/`Notify` `ObjId` from `self.object()` is present in local object maps, or omit cross-node `cap_derive`/`cap_move`/`untyped_retype` grants.
- **Smallest correction:** Handle remote destination `CSpace`s in `cap_derive`/`cap_move`/`untyped_retype` by creating cross-node grants per contract line 836; add the missing calls (`ReplyRecv`, `Sched*`, `ASpace*`, `CSpaceGrow`, `IoSpace*`) to `capability_arguments()`; and reject `self.remotes.contains_key(&id)` with `Err(Error::Invalid)` in local syscalls taking secondary object capabilities.

### F8 — `UnitRequest` retry is lost forever if a unit role cycles back to `sent_to` before `roles_unit()` runs (`Model`)

- **What is wrong:** `send_unit_request` (`roles.rs:231-248`) leaves `sent_to = Some(holder)` unchanged when `!usable` (e.g., `Body::UnitAnswer(done: false)` arrives while the role is `Handing`). If the target takes the role and hands it back to `holder` (`Some(word.holder()) == sent_to`) before the requester runs `roles_unit()`, `roles_unit` (`roles.rs:393`) skips the request because `Some(word.holder()) != *sent_to` is false, leaving the caller in `Wait::Node` forever.
- **Where:** `model/src/roles.rs:231-248, 291-294, 386-403`.
- **How known (`run`):** `adversarial_review7.rs::f10_late_handed_trace_and_unit_request_retry_lost_after_handover_cycle` (passes: `sys.node(0).woken(attacher) == None` after `200 ms`).

- **Smallest correction:** Clear `sent_to = None` in `send_unit_request` whenever `!usable` (or when `UnitAnswer(false)` arrives), and compare `(word.holder(), word.epoch())` against `(sent_to, epoch)` in `roles_unit()`.

### F9 — `thread_move` makes a moved source thread runnable if `thread_resume` ran during transit, and omits `in_move` freezes on `sched_count`, `task_attach`, and `task_revoke` (`Model`)

- **What is wrong:** Contract line 675 states that `thread_resume(source)` during `thread_move` clears suspension so `source` runs *"only if the move was refused"*, and freezes `source` and its context until the answer. In `moved()` (`moves.rs:236-245`), when `outcome.is_ok()`, `source` has its registers zeroed and `home` set to `None`, **without setting `suspended = true`**, so calling `ThreadResume(source)` during transit leaves `source` in `runnable()` with `home == None` and zeroed registers after the move succeeds. Additionally, `sched_count` (`sched.rs:702-722`) and `task_attach` (`tasks.rs:45-79`) omit `in_move` `Busy` checks, and `task_revoke` → `stop()` (`tasks.rs:148`) detaches an `in_move` thread from its task mid-move.
- **Where:** `Docs/architecture/kernel-interface.md:675`; `model/src/moves.rs:236-245`; `model/src/sched.rs:702-722`; `model/src/tasks.rs:45-79, 138-149`.
- **How known (`run` + `read`):** `adversarial_review7.rs::f9_thread_move_resume_makes_zombie_runnable_and_missing_freeze` (passes: `ThreadResume`, `SchedCount`, and `TaskAttach` all return `Done` mid-move, and `src_id` is in `runnable()` post-move); `read` for `task_revoke` → `stop()`.
- **What a kernel author would do wrong:** Allow `thread_resume` to leave an empty, unscheduled post-move thread object marked runnable, or mutate `counted`/task membership while `Moved` is in flight.
- **Smallest correction:** Set `live(&mut self.threads, source).suspended = true` on `outcome.is_ok()` in `moved()`, reject `sched_count` and `task_attach` with `Error::Busy` when `in_move`, and skip/defer detaching `in_move` threads in `task_revoke`/`stop()` until the move settles.

### F10 — Spurious `Refused` trace on normal late `Body::Handed`, shared per-node `Refused` rate-limit DoS across peers, and minor `needed()` / `core_start` gaps (`Model`; minor `Contract` note)

- **What is wrong:**
  1. **Late `Body::Handed` traced as `Refused` (`run`):** If the hand-over target completes step 5 (`take_handed()`) before `Body::Handed { role }` is delivered, `misdirected()` (`remote.rs:649-655`) rejects `Body::Handed` because the word is already `Held` and records a spurious `TraceCode::Refused` entry on a normal hand-over.
  2. **`TraceCode::Refused` bucket is shared across all peers (`run`):** `debug.rs:179-207` indexes `self.limits` by `code` (`11`) per receiving node (`16/ms`), matching contract line 1295 (*"Windows are counted per node"*). One noisy peer sending 16 bad `Release` packets in 1 ms suppresses `Refused` traces from every other peer in that window (and sustained invalid packets roll the 256-entry kernel trace ring over `16 ms`), while stale-generation `R0` drops (`!current`, `remote.rs:503`) emit no trace at all.
  3. **Minor mismatches (`read`):** `core_start(CORE_START_FRESH)` (`recovery.rs:124`) checks `module < modules` without checking whether `module` is flagged as a first service (`kernel-interface.md:1172`); `needed()` (`recovery.rs:465-473`) watches only `Request::Call` peers directly (relying on the 1 s cyclic sweep for `Move`, `Carry`, `Transfer`, `Revoke`, and `Unit` peers); and `revoked_grantee()` (`recovery.rs:970`) returns `None` if `grants[me]` no longer contains `grant` (only reachable after `released()` frees a revoking grant prematurely per F1).
- **Where:** `Docs/architecture/kernel-interface.md:855, 1172, 1295`; `model/src/remote.rs:502-521, 649-655`; `model/src/recovery.rs:124, 465-473, 970`; `model/src/debug.rs:177-211`.
- **How known (`run` + `read`):** `adversarial_review7.rs::f10_late_handed_trace_and_unit_request_retry_lost_after_handover_cycle` (late `Body::Handed` trace); `system::review7_unit_tests::refused_bucket_is_per_node_and_serial_generation_wrap_correctly` (peer 1 starving peer 2's `Refused` trace); `read` for `core_start`, `needed()`, and `revoked_grantee()`.
- **What a kernel author would do wrong:** Alert on `TraceCode::Refused` during normal unit hand-overs, let one buggy peer silence audit trails for all other peers, or attempt to start a non-first-service boot module.
- **Smallest correction:** Include `epoch` in `Body::Handed` and ignore already-completed epochs (`word.epoch() >= handed_epoch`) silently; consider per-peer rate limiting for `TraceCode::Refused` (or separate ring counters); check first-service module flags in `core_start(FRESH)`; and include all active request peers in `needed()`.

### F11 — `liveness.rs` and `way_out` omit key states, multi-node migration, double faults, and stuck `Request`/`Wait::Node` checks (`Model tests`)

- **What is wrong:** Auditing `liveness.rs` across all 6 scenarios (`grant`, `reserve`, `kill`, `seal`, `hand`, `attach`: `RUNS=136`, `WAY_OUT=136`) shows that `liveness.rs` runs only three nodes pinned 1:1 to three separate cores with a single crash per run:
  - **States reached in `liveness.rs` (`run`):**
    - `MemberState`: 7 of 8 (`Dead`, `Fenced`, `Fencing`, `Live`, `Sealed`, `Sealing`, `Unfenced`; **never `Starting`**).
    - `Evidence`: 4 of 7 (`Kill`, `None`, `Stale`, `Stuck`; **never `SelfReported`, `Retire`, `Host`**).
    - `RoleState`: 3 of 3 (`Handing`, `Held`, `Vacant`).
    - `GrantState`: 2 of 3 (`Live`, `Pinned`; **never `Revoking`**).
    - `CoreState`: 4 of 6 (`Hung { nmi: true }`, `Looping`, `Parked`, `Running`; **never `Hung { nmi: false }`, `InitPending`, `Off`**).
  - **Prompt scenarios/states no test in `liveness.rs` (and some in no repo test) reaches:** (1) `CorePlace` / co-hosted nodes on one core (`parked_block`, `HostSealed`, co-hosted `RESUME`, `CORE_STOP_RETIRE`); (2) phantom-node boundaries; (3) `Unfenced` driver dying and redrive; (4) two nodes dying in turn / recovering node dying during R0–R6 / fast restart before `unpin()`; (5) chains of hand-overs / ring of sealing nodes; (6) `thread_move` or `CapRevoke` in flight across crashes (`Starting` never lingers across events in `System::start_node`); and (7) **`way_out` (`liveness.rs:271-300`) checks only `MemberState`, `RoleWord`, and `grant_entries()`** — it would **pass** even with permanently stuck `Wait::Node` threads, leaked `requests`/`outstanding`/`held_requests`, orphan `UseEntry`s, or stranded `kernel_space` anchors.
- **Where:** `model/tests/liveness.rs:1-378`.
- **How known (`run` + `read`):** Instrumented `liveness.rs::audit_liveness_coverage` (`136` runs, all passing) + `grep` across `model/tests/`.
- **What a kernel author would do wrong:** Rely on `liveness.rs` and `way_out` passing as evidence that `Request`, `Wait::Node`, co-hosted placement, `Revoking`, `Starting`, and double-crash recovery have no stuck states.
- **Smallest correction:** Extend `way_out` to assert that no thread remains in `Wait::Node`, `requests` / `outstanding` / `held_requests` are empty once quiet, and `kernel_space` holds no orphan anchors without grant entries; and add bounded scenarios in `liveness.rs` covering `CorePlace` co-hosting, `CapRevoke`, `ThreadMove`, `CORE_START_FRESH`/`RESUME`, and double crashes.

## What was checked and found right

- **Grant name & serial width/wrapping (`read` + `run`):** Grant slots are 12 bits (`GRANTS = 4096`), nodes are 10 bits (`NODES_MAX = 1024`), serials are 30 bits wrapping `(serial + 1) & 0x3FFF_FFFF`, `RoleWord::epoch` is 30 bits, and `Member::generation` is 32 bits (`wrapping_add(1)`). Every check uses `==`/`!=` (never `<`/`>`), so `0x3FFF_FFFF -> 0` and `u32::MAX -> 0` wrap cleanly (`review7_unit_tests::refused_bucket_is_per_node_and_serial_generation_wrap_correctly`); a slot would need `2^30` frees within a single generation to collide with a sealed holder's `serial`.
- **Sealed nodes never observed or accused of `Stale`/`Stuck`/`SelfReported` (`read`):** `observe_needed()` skips `!writes(node)` (`recovery.rs:500`), and the gate / `recovery_unit` accuse only `Starting | Live | Sealing` for observation evidence (`recovery.rs:585-588`), allowing `Kill`, `Retire`, and `Host` on `Sealed`.
- **Two nodes dying in turn, recovering/unfenced driver dying and redriven, and R6 reserve freeing (`run` + `read`):** Verified in `positive_recovery_edges_and_handover_ring_and_unfenced_redrive` and `recovery.rs:602-621, 1056-1078`: when `Unfenced` node 1's driver (node 0) hangs, surviving node 2 takes the driver field, re-fences node 1, and drains to `Dead` once VMX exits; `barrier_unit()` clears `Ownership::taken(Reserve(j), g)` chunks back to `Ownership::free(Reserve(j))` at R6 and vacates reserve/plain roles.
- **Hand-over when target seals (`run`):** In a 3-node system (`positive_recovery_edges_and_handover_ring_and_unfenced_redrive`), sealing the target of a `Handing` unit role runs `take_handed()` (step 5 + synchronous R1 clear) and passes the role onward to the remaining live node cleanly.
- **Phantom nodes & last-live-node protection (`read`):** Checked `cores.rs:884-913` and `recovery.rs:220-229`: `core_stop` excludes phantom nodes (`!self.shared && n != self.node`), refusing to kill/seal/retire the sole active node (`Error::Busy`), and `check_cores` enforces invariant 86.
- **Wait cancellation & `thread_move` destruction (`read`):** `ThreadCancel` leaves `Wait::Node` of `ThreadMove` active until answered, and `CapDelete` on an `in_move` `source` or `sched` returns `Error::Again` (`cores.rs:771-830`, `caps.rs:245`), ending with `Gone` on R0 if the destination node is accused while live.
