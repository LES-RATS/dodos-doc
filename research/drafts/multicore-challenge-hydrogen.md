# Independent Challenge to the DodOS Multi-Core Design

This document challenges the multi-core architecture of DodOS as specified in [kernel-interface.md](file:///Users/btw/Documents/repos/Docs/architecture/kernel-interface.md) (commit `3bc7597`) and implemented in `dodos-kernel` (branch `model`, commit `2afc901`). It inventories every cross-node protocol, audits the seven model review rounds and the design review, critiques correctness and real-world performance against `trials/multicore` (`f9933bd`) and adversarial model tests (`challenge_breaks.rs`, 8 tests passing on `4k`, `16k`, and `32k` geometries), checks eighteen primary-source precedents, and lays out concrete alternatives that preserve the six fixed design constraints.

## 1. Complete Cross-Node Protocol Inventory

### 1.1 Wire Messages (`remote.rs`)

The executable model defines 18 inter-kernel ring message variants in [`Body`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/remote.rs#L37-L138), sent over fixed per-ordered-pair rings (`16 MB` ceiling on proxy buffers per node at `NODES_MAX = 1024`).

| Protocol / Message Family | Why it exists | Concrete application need | Model states & messages | Crash behavior at each step (model & contract) |
|---|---|---|---|---|
| **Forwarded call (`Request`, `Answer`, `Cancel`)** | Lets a thread invoke a capability held on another node (`kernel-interface.md:849–855`, `remote.rs:38–63`). | Calling a service pinned on another core when capabilities are held remotely rather than re-bound to local rings. | 2 proxy states (`busy`, `cancelled`), 3 messages (`Request`, `Answer`, `Cancel`), `PROXIES_PER_PEER = 16` slots per peer (`remote.rs:477`). | **Sender dies before `Answer`:** receiver `isolate()` cancels waiting proxies and cleans R2 (`recovery.rs`), but `Thread::destroy` leaks proxies on `Transfer`/`Revoke` wait unless explicitly unlinked (`R7 F5`, `Verify-New`). **Target dies before `Answer`:** live callers wait in `Wait::Node` until `R2` wakes them with `Error::NodeDead`. **Ring order race:** stale `Request` after slot reuse delivers to a third node's reused grant (`challenge_breaks.rs` test #3). |
| **Capability transfer (`TransferAsk`, `TransferGrant`, `Refused`, `Returned`)** | Transfers capabilities inside `send`, `reply`, `call`, `recv` across nodes (`remote.rs:64–95, 860–1180`). | Passing frame, endpoint, or notify handles across cores in user-space IPC. | `GRANTS = 4096` grant entries/node (`128 B` each = `512 KB`) + `4096` use entries/node (`32 B` each = `128 KB`). 4 messages. | **Granter dies before `TransferGrant` arrives:** grant table cleared at reload; grantee drops uses at reclaim `R4`. **Grantee dies after `TransferAsk`:** `Returned` sent to wrong generation unless serial matches; `R7 F6` showed `Answer` vs `Refused` race drops moved caps in `kernel_space`. **`Refused` on `Home` return:** strands remaining entries in all-or-nothing check (`R7 F6`). |
| **Cross-node revocation (`Revoke`, `RevokeStep`, `Release`)** | Implements cascading `cap_revoke` / `cap_delete` across nodes (`remote.rs:96–113, 1185–1385`). | Single-action revocation across cores (`task_revoke` / server isolation). | 3 messages + `RevokeState` / `pinned` mask on grants (`R3`). | **Grantee dies before `Release`:** granter stalls in `Wait::Node`; reclaim sets `pinned` (`R3`) and clears via `unpin()` once `Dead`. **New bug found (`challenge_breaks.rs` test #7):** retrying `CapDelete` while grantee is `Fencing` leaves caller stuck forever even after grantee becomes `Dead` and `unpin()` frees the grant. **Stale `RevokeStep` in legal FIFO order:** breaks Invariant 58 on grant reuse and hangs a third-node revoker forever (`challenge_breaks.rs` test #2). |
| **Thread migration (`Move`, `Moved`)** | Moves a suspended thread, its FPU/feature state, and context budget via `thread_move` (`moves.rs:1–270`, `remote.rs:114–125`). | Explicit load balancing across cores or moving to P/E cores (`heterogeneous-cores.md`). | Thread `in_move` lock flag (`kernel-interface.md:675`), 2 messages (`Move`, `Moved`), serialized thread register/budget state. | **Target dies before `Moved`:** `isolate()` originally omitted `Request::Move`, hanging caller (`R6 F4`, fixed by adding `Move` tracking). **Crash/reuse:** `Body::Move` has no `serial`; late `Move` overwrites or panics a reused slot (`R7 F3`, `Verify-New N2/N2-S1`). **`thread_resume` during move:** leaves source runnable or inconsistent (`R7 F9`). **Scheduler deleted mid-move:** steals unrelated context / breaks `admitted` sum (`R6 F11`). |
| **Role hand-over (`Handed`)** | Transfers singleton platform/unit roles cleanly (`roles.rs:1–536`, `remote.rs:126–128`). | Handoff of driver manager, IOMMU, GIC/IOAPIC, or reserve owner without panic. | `RoleState` (`Unclaimed`, `Held`, `Handing`, `Claimed`), 1 wire message (`Handed`) + shared `roles` table word. | **Recipient crashes or becomes `Sealed` mid-handoff:** `R6 F6` found step-4 hand-over skipped `R1` barrier and deadlocked against `CORE_STOP_SEAL`. **Stale `Handed`:** traces spurious `Refused` (`R7 F10`). |
| **Unit / IOMMU requests (`UnitRequest`, `UnitAnswer`)** | Forwards `iospace_attach`, `iospace_detach`, `iospace_invalidate` to the IOMMU role holder (`roles.rs:280–490`, `remote.rs:129–133`). | User-space DMA drivers running on any core other than the hardware/IOMMU role holder. | `UnitRequest` table per unit + retry queue (`sent_to`, `epoch`), 2 messages. | **Role holder dies mid-request:** caller retries when role moves; **lost-request bug (`challenge_breaks.rs` test #5, `R7 F8`):** if role bounces back to `sent_to` at a new epoch before `roles_unit()` polls, retry is lost forever. **Thread destroyed mid-detach (`R7 Opus N1`):** leaks active IOMMU context entry. **New bug found (`challenge_breaks.rs` test #6):** `roles::rebuild()` skips `!writes(Sealed)` nodes, wiping live attached IOMMU entries of a `Sealed` node that later resumes. |
| **Work stealing & perf hints (`Carry`, `CarryDone`, `Ping`)** | Pulls runnable work onto idle cores (`core_idle`) and relays `core_perf` hints (`remote.rs:134–137`). | **None found** for user-space Wasm apps (which cannot share threads across cores in WASI 0.3.0); speculative kernel idle-balance hook. | `core_beacons`, ring sweep via `Ping`, 3 messages (`Carry`, `CarryDone`, `Ping`). | **Node crashes holding `Carry`:** work silently dropped unless source recovers local runnable state; idle sweep falsely marks co-hosted/sealed nodes stale unless exempted (`R6 F2`). |

### 1.2 Shared-Memory Table & Gate Protocols (`table.rs`, `recovery.rs`, `roles.rs`)

Beyond rings, nodes coordinate by writing single-writer fields inside a globally coherent [`Table`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/table.rs#L148-L221) (`kernel-interface.md:756–1240`):

| Protocol | Why it exists | Concrete app need | States & footprint | Crash behavior |
|---|---|---|---|---|
| **Membership, Fencing & Reclaim (`R0`–`R6`)** (`recovery.rs`) | Detects dead/hung peers (`Evidence::Idle`, `Stale`, `Fence`), isolates hardware, rebuilds shared tables, and reloads without reboot (`kernel-interface.md:1025–1215`). | Recovering a crashed core without losing other cores' Wasm apps or persistent state. | 7 member states (`Unused`, `Starting`, `Live`, `Sealed`, `Unfenced`, `Fencing`, `Dead`), 7 reclaim phases (`R0`–`R6`), `acked` bitmap `O(n^2)` (`8 MB` at `1024` nodes), per-node `beacons` + `core_beacons`. | **Fencer dies while target is `Unfenced`:** `R6 F9` / fixed by driver sweep, except **new bug (`challenge_breaks.rs` test #8):** ARM64 `FENCE_CLASS_SIGNALLED` replacement failure wedges node permanently in `Unfenced`. **Co-hosted node seal/stop:** `R6 F7`, `R6 F8`, `R7 F4`, `R7 Opus N4` showed `ParkSelf`, `save_seal`, and last-live checks repeatedly misbehave when two logical nodes share a physical core. |
| **Memory Ownership & Write Gate** (`memory.rs`, `table.rs`) | Moves `2 MB` chunks via `memory_take` / `give` / `split` and guards CPU/IOMMU page-table writes against wild pointers (`kernel-interface.md:756–905`). | Dynamic memory balancing between cores without a shared kernel allocator. | 1 ownership word (`8 B`) + 1 `GateWord` (`8 B`) + `512 B` descriptor per `2 MB` chunk; `maps`, `classes`, `owners` in `Table`. | **Owner dies after fresh restart:** chunks and PCIe identifiers (`challenge_breaks.rs` test #4, `R7 Argon 1.1`) or device entries (`R7 Opus S1/S2`) stay permanently wedged to the dead generation because reclaim/restart checks `Owner::Node(x)` against current generation instead of letting dead generations fall to unclaimed/reusable. **Unmapped check bug:** device/read-only leaves miscount `maps` (`R7 DeepSeek F6`, `Verify-New N4/S3`). |

### 1.3 Contracted Cross-Node Features Unimplemented or Unproven in `dodos-kernel`

Reading `kernel-interface.md` (`lines 849–905, 1877–1894`) alongside [`model/src/lib.rs`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/lib.rs) shows seven contracted cross-node surfaces absent or crashing in the model:
1. **Multi-node address-space core groups (`D-027`):** Deferred; no cross-node page-table replication or TLB shootdown exists in the model.
2. **Cross-node capability derivation/retyping (`cap_derive`, `cap_move`, `untyped_retype`):** `contracted_cross_node_derive_and_secondary_cap_panics` ([`challenge_breaks.rs`](file:///Users/btw/.t3/userdata/providers/antigravity/3ee7deb29a315284788021b40513bfa34546a79204bcbe2cc59c23215eb83836/antigravity-acp/brain/66f45d7e-bd92-44f2-b987-f23583dce18e/scratch/dodos-challenge/model/tests/challenge_breaks.rs#L193)) proves remote `CapDerive` panics at `lib.rs:1635` and secondary remote `SchedBind` panics at `sched.rs:620`, confirming `R7 Hydrogen F7` and `DS-N1-S1`'s 7 additional panicking syscalls.
3. **Capabilities returned in `reply` / `reply_recv` across nodes (`kernel-interface.md:1894`):** Left unimplemented/open.
4. **Non-IOMMU unit role operations:** IOAPIC routing, GIC distributor/ITS (`GICD_IROUTER`), RISC-V APLIC/IMSIC, and MSI-X masking/claim requests exist only in prose (`kernel-interface.md:698–706, 1724`), not in `roles.rs`.
5. **Write-gate ISA mechanisms (`kernel-interface.md:902, 1889`):** No bare-metal mechanism (`WRSSQ`, `CR3` gate, `TTBR1`/`SKEE`, `satp`) is built or measured on reference silicon; only model checks exist.
6. **Timed recovery deadlines & reserve enforcement (`recovery.rs:8–10`):** `SETTLE_NS` and `NMI_GRACE_NS` timeouts and recovery-reserve memory budgets are unmodeled; `recovery.rs` injects state transitions directly.
7. **Console pacing, DMA fault delivery, and gdb stub release barrier (`kernel-interface.md:1877–1894`).**

## 3. Technical Critique

### 3.1 Correctness

#### (1) Unsettled message & delivery ordering breaks even legal FIFO execution
Round 7 verifiers patched `System::deliver` to forbid overtaking within a `(from, to)` ring, which already broke **three existing tests in the upstream suite** ([`Verify-New`](file:///Users/btw/Documents/repos/Docs/reviews/2026-11-16-model-review-7-verify-new-findings-by-hydrogen.md#L66-L70)). Worse, even **with** strict per-pair FIFO delivery enforced, cross-pair causality is absent:
- [`stale_revoke_step_fifo_order_inv58_and_forever_wait`](file:///Users/btw/.t3/userdata/providers/antigravity/3ee7deb29a315284788021b40513bfa34546a79204bcbe2cc59c23215eb83836/antigravity-acp/brain/66f45d7e-bd92-44f2-b987-f23583dce18e/scratch/dodos-challenge/model/tests/challenge_breaks.rs#L241-L342) proves in legal pairwise FIFO order that a slow `RevokeStep` from node 0 to node 1 lands *after* node 1 released grant `0` and node 0 reused slot `0` for node 2, tripping **Invariant 58** and hanging node 2's `CapRevoke` forever in `Wait::Node`.
- [`stale_request_signals_third_node_notify_in_fifo_order`](file:///Users/btw/.t3/userdata/providers/antigravity/3ee7deb29a315284788021b40513bfa34546a79204bcbe2cc59c23215eb83836/antigravity-acp/brain/66f45d7e-bd92-44f2-b987-f23583dce18e/scratch/dodos-challenge/model/tests/challenge_breaks.rs#L344-L385) proves in legal FIFO order that an older `Body::Request(Signal)` hits a newly granted `Notify` occupying reused grant slot `0` belonging to a third node, delivering a forged signal across isolation domains.
- **No explicit model check enforces causal ordering across `node A -> node B -> node C`** (e.g., `Move`/`Release`/`RevokeStep`/`UnitRequest` vs shared `Table` visibility), because real hardware IPIs, posted PCIe/MSI writes, and ring polls interleave asynchronously.

#### (2) De facto shared mutable kernel state (`table.rs`) contradicts the core thesis
DodOS claims "one kernel per core, no shared mutable kernel state." Yet [`Table`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/table.rs#L148-L221) places 18 globally coherent shared tables in shared RAM (`owners`, `maps`, `classes`, `devices`, `identifiers`, `members`, `roles`, `fences`, `beacons`, `core_beacons`, `placed`, `unusable`, `units`, `reports`, `grants`, `uses`, `admitted`, `off`), and [`aspace_map` / `unmap` / `protect`](file:///Users/btw/Documents/repos/dodos-kernel/model/src/memory.rs) mutate `table.maps` and `table.classes` atomically on ordinary single-core memory operations. Rather than avoiding shared mutable state, DodOS replaces conventional fine-grained locks with **hardware single-writer conventions enforced by an unbuilt, unmeasured write gate**. If a kernel bug bypasses or mis-implements the write gate (`gate-page-tables.md:38–70`), coherent shared tables remain physically writable.

#### (3) Hardware & firmware assumptions that do not hold across target platforms
- **`SETTLE_NS = 1 ms` ([`abi/src/machine.rs:235`](file:///Users/btw/Documents/repos/dodos-kernel/abi/src/machine.rs#L235)):** Assumes waiting 1 ms after fencing guarantees posted DMA/MMIO/memory writes from a halted core have drained before another core reclaims roles or unmasks I/O; no x86/ARM64/PCIe spec backs 1 ms for deep posted fabrics or hung DMA engines without explicit IOMMU/root-complex drain barriers.
- **x86 `INIT` / SIPI / BSP / `VMX` (`fencing-without-cooperation.md:68–82`):** The bootstrap processor (`apic_id == 0`) **cannot** be parked cleanly or safely restarted via `INIT`/SIPI without platform firmware/BIOS quirks (`symmetric-nodes-recovery.md:37` marks BSP irreducibility); `INIT` is blocked in VMX root operation (`fencing-without-cooperation.md:74`), and virtualized guests under KVM/Hyper-V cannot issue arbitrary physical `INIT`/`SIPI` sequences or bypass nested VM exits reliably.
- **ARM64 SDEI / PSCI / `FEAT_NMI` ([`2026-11-16-model-review-7-mistral.md`](file:///Users/btw/Documents/repos/Docs/reviews/2026-11-16-model-review-7-mistral.md#L34-L47)):** EL3 SDEI only accepts an EL2 hypervisor client (`ELC = EL2`), not an EL1 kernel (`R6 F1`); cores hosting a resident Trusted OS refuse `PSCI CPU_OFF`, and PSCI provides no cross-core remote stop call; on `FEAT_NMI` cores, `PSTATE.ALLINT` masks NMI anyway (`R7 F2`).
- **RISC-V `fence_hart` (`R6 F2`):** Relies on a custom unratified SBI extension (`fence_hart`) that no shipping RISC-V firmware implements.
- **IOAPIC EOI / MSI-X / warm-reset persistence:** IOAPIC level-triggered EOI cycles and MSI-X masking assume role-holder responsiveness across crashes; warm-reset reload assumes DRAM contents of peer kernels survive reset intact despite platform memory-scrubbing or TME-MK / DRAM refresh disruption on cold/warm reset paths.

#### (4) Concurrent and double failures broken on `2afc901` (newly written & run tests)
All 8 tests in [`challenge_breaks.rs`](file:///Users/btw/.t3/userdata/providers/antigravity/3ee7deb29a315284788021b40513bfa34546a79204bcbe2cc59c23215eb83836/antigravity-acp/brain/66f45d7e-bd92-44f2-b987-f23583dce18e/scratch/dodos-challenge/model/tests/challenge_breaks.rs) pass on `4k`, `16k`, and `32k` page geometries (`8/8 passed` after final edit), proving three newly found double-failure / concurrent races alongside five known protocol defects:
1. **`unit_rebuild_wipes_sealed_nodes_attached_iommu_entry` (`challenge_breaks.rs:509–588`):** When node 1 has an attached PCIe device and becomes `Sealed` (e.g., co-hosted parking or `core_stop`), then node 2 dies and node 0 runs `roles::rebuild`, `rebuild()` checks `writes(Sealed) == false` and wipes node 1's active device entry from `table.units[role].entries`. When node 1 resumes via `CORE_START_RESUME`, its local `IoSpace` still believes the device is attached (`Err(Busy)` on re-attach; IOMMU hardware state diverges from `Table`).
2. **`revoke_retry_while_grantee_fencing_hangs_thread_forever_after_unpin` (`challenge_breaks.rs:590–652`):** If node 0 calls `CapDelete` on a granted cap, node 1 transitions to `Fencing`, and node 0's thread is cancelled/restarted and retries `CapDelete` before node 1 reaches `Dead`, the caller parks in `Wait::Node(1)` after `pinned` was already set during `Fencing`—so when node 1 reaches `Dead` and `unpin()` clears the grant, the second waiter in `Wait::Node` is **never woken** (`ThreadState::Blocked` forever).
3. **`arm64_signalled_replacement_resume_failure_wedges_unfenced` (`challenge_breaks.rs:654–716`):** On an ARM64 `FENCE_CLASS_SIGNALLED` core (`allows_replacement() == true`) parked while `Sealed`, if its replacement `CORE_START_RESUME` fails because the image block is unreadable (`Error::Denied`), the model writes panic, calls `ParkSelf`, and wedges permanently in `MemberState::Unfenced` with no watchdog recovery path.

### 3.2 Performance and Real Use

#### (1) Wasm has no threads; multi-core services hit the wrong bottleneck
Per [wasm-abi.md](file:///Users/btw/Documents/repos/Docs/architecture/wasm-abi.md#L126-L128), **WASI 0.3.0 (11 June 2026) has no threads**, `shared-everything-threads` is unimplemented in Wasmtime, and async component calls already cost **3.5× native** (`wasm-abi.md:124`). Parallel Wasm apps run as multiple separate component instances communicating by channels/streams, so they rarely need shared multi-core page tables or cross-core capability-tree splits (`D-027`). Conversely, DodOS's real multi-threaded workloads—native Rust storage/network services, `llama.cpp`, and Ladybird—require shared address spaces (`D-027`, currently deferred!) or fall back to cross-node message forwarding across `16`-slot proxy buffers.

#### (2) Fixed per-node and $O(n^2)$ memory cost (2 cores vs. 64 cores vs. 1024 ceiling)
Every logical node carries static kernel tables bounded for `NODES_MAX = 1024`:
- **Fixed per-node allocations (`abi/src/machine.rs`, `kernel-interface.md:833, 1570`):** `GRANTS` (`4096 × 128 B = 512 KB`) + grant uses (`4096 × 32 B = 128 KB`) + `2 × DebugArea` (`139 KB`) + `PROXIES_PER_PEER × 1 KB × n` (`1 MB/node` at 64 cores; `16 MB/node` at 1024) + `16 MB` per-node floor (`nodes-memory-devices.md:52–68`).
- **$O(n^2)$ global tables:** `acked` (`1 bit` per pair = `128 KB` at 1024 nodes) and `core_roots` (`64 B` per pair? At 1024 nodes `1024^2 × 64 B = 64 MB`; at 64 cores `256 KB`).
- **Per-RAM global tables:** `owners` (`8 B / 2 MB` = `256 KB` per `64 GB`) + `GateWord` (`8 B / 2 MB` = `256 KB` per `64 GB`) + descriptor bytes (`512 B / 2 MB` = `16 MB` per `64 GB` if all page tables, proportional when sparse) + `page_classes` (`1 B / 4 KB` = `16 MB` per `64 GB`).
- **Summary:** At **2–4 cores**, static multi-node overhead is small (~`1.5 MB` kernel tables + floors), but at **64 cores** static `16 MB` floors + proxy tables consume **`> 1 GB`** before a single app starts (`heterogeneous-cores.md:160` notes 24 cores consume `<0.6%` of 64 GB, ignoring 64–128-core servers or `1024` scale where per-node proxies alone hit **`16 GB`**).

#### (3) Heterogeneous P/E cores and IRQ vs. driver cores
- **P/E asymmetry (`heterogeneous-cores.md:78–125`):** Hardware thread hints change every tens of milliseconds, whereas cross-cluster migrations only pay off every **4–5 seconds** on Apple silicon (`0.1s` intra-cluster). Automatic `core_idle` ring stealing (`Carry`/`Ping`) blindly pulls threads across P/E clusters or burns IPIs, while manual `thread_move` incurs cross-node state serialization + `Moved` latency.
- **IRQ vs. driver core:** Interrupt routing registers on ARM64 (`GICD_IROUTER`, ITS) and RISC-V (`APLIC`/`IMSIC`) require MMIO/gate validation (`R7 Mistral F3`), and decoupling an IRQ core from a driver core adds an inter-core IPI + ring hop on every unmasked hardware interrupt unless `irq_claim` co-locates interrupts with the driver node.

#### (4) Head-to-head cost vs. shared-state/lock kernel (`trials/multicore` @ `f9933bd`)
Using the clean `k = 4` P-core rows in [`results-mac-m5.md`](file:///private/tmp/claude-501/-Users-btw-Documents-repos/57992ac2-1573-4f43-a999-1ff9c7f97c7a/scratchpad/trial/trials/multicore/results-mac-m5.md) (noting `ipi = 0` or `1000 ns` and `tlb = 100 ns` are *modelled* on M5 with a `41.7 ns` clock, not bare-metal x86/ARM measurements):
- **Reads (`a1` / `a1t`):** With lock-free seqlock slot reads (`Series 3 fine`), Candidate 3 (shared group) leads Candidate 1 (per-core rings) by **2–4%** at `1%` writes (`ipi = 1 µs`) and by **27–32%** at `10%` writes (`1.54–1.65×` at `k = 8`). Candidate 1's only win on reads is lower `p99`/`p99.9` tail (`1.04× W` vs `1.7× W` p99 / `2.1× W` p99.9 in Candidate 3 at `W = 1 µs, 10%` writes).
- **Capability edits (`a1` change latency):** Candidate 3 is **2.3–9.6× faster** (`0.25–1.2 µs` p50 vs `1.6–4.4 µs` for Candidate 1 `fair`) because Candidate 1 pays remote home-node round trips and IPI acknowledgments.
- **IPC (`a2t`):** Adding per-endpoint locks shrinks Candidate 1's IPC lead from `4–7%` (up to `2.3×` under `Series 2` coarse lock at `k = 8`) down to **1–2%** (`624k vs 638k` ops/s at `ipi = 0, W = 50 ns`; `354k vs 362k` at `ipi = 1 µs, W = 200 ns`)—within noise.
- **Many-to-one Signals (`a3n`):** Candidate 1 wins `6–8%` against a locked notify (`1.80M vs 1.94M` at `W = 200 ns`), though atomic `OR` drops wait-tail bottlenecks (`344 µs -> 0.87 µs` at `k = 8, W = 1 µs`), and **1-µs per-message IPIs without batching collapse Candidate 1 to 0.2–0.46× group throughput** (`p99.9 = 0.85–6 ms`).
- **Unmap (`b` / `br`):** At `ipi = 1 µs` with all threads unmapping (`W <= 200 ns`), Candidate 3 achieves **1.44–1.55×** throughput (`1.50M vs 1.17M` at `W = 50 ns`), and `1.55–2.01×` in `br` (`Series 4`), because Candidate 1 pays home-serialize + fan-out hop + reply messages.
- **Gate overhead never measured in `trials/multicore`:** Real DodOS also pays gate checks on every page-table/root mutation (`WRSSQ` `9.3` cycles vs `0.8` `MOV` on Tiger Lake; `MOV CR3` ~`200` cycles / `200–400` round-trip; `SKEE`/`Hilps` `284–424` cycles; hypercall `497–961` cycles, [`gate-page-tables.md:276–279`](file:///Users/btw/Documents/repos/Docs/research/drafts/gate-page-tables.md#L276-L279)), plus unmeasured cross-range subtree revocation lock ordering in Candidate 3.

## 5. Concrete Alternatives (Preserving All Six Fixed Points)

Every option below preserves all six constraints: **(1) one kernel per core**, **(2) no shared mutable kernel state**, **(3) single-core recovery without machine reboot**, **(4) no kernel heap**, **(5) capability security**, and **(6) costs paid only at failure or rare events**.

### Option A: Minimal Rings + Static Fence + Recovery Only (Push All Cross-Core Services/Cap Names to User Space)
- **Design:** Strip capability forwarding, remote syscalls, `thread_move`, and cross-node revocation out of the kernel. Each kernel manages only its own core's objects, its local `2 MB` chunks (`owners`), static `GateWord` checks, and SPSC shared memory frames (`Frame` grants only, keyed by owner generation). A user-space coordinator handles thread placement, multi-core process orchestration, and capability naming over shared rings.
- **Removed contract lines & states:** Cuts `remote.rs` `Request`/`Answer`/`Cancel`, `TransferAsk`/`TransferGrant`/`Refused`/`Returned`, `Revoke`/`RevokeStep`/`Release`, `Move`/`Moved`, `Carry`/`CarryDone`/`Ping` (all 15 of 18 `Body` variants), `PROXIES_PER_PEER` (`16 MB/node` ceiling), `RemoteRef` proxy resolution (`kernel-interface.md:849–855`), and `in_move` freeze rules (`lines 675–683`).
- **New costs & when paid:** User-space services pay one extra ring hop (`~0.1–0.5 µs`) only when marshaling cross-core IPC (`Frame` ring already zero-copy); recovery drops from `R0–R6` + `unpin` + `isolate` to resetting dead frames' generation checks (`paid at failure only`).
- **Unserved user/app needs:** Transparent single-capability remote syscall forwarding (`cap_derive` / `send` across cores); kernel-driven `thread_move` and `core_idle` stealing.
- **What to measure:** Round-trip latency of a user-space multi-core sDDF-style ring service vs `remote.rs` kernel proxy forwarding on x86-64.

### Option B: Static Core & Memory Partitions (LionsOS / Tessellation Pattern)
- **Design:** Partition physical cores, chunks, and PCIe devices at boot into fixed fault domains (`1` core per kernel, or `2–4` cores per L3 cell if `D-027` uses `Candidate 2`), communicating solely via pre-allocated shared SPSC rings and immutable frame grants established at domain creation. A failed core/domain is restarted cleanly from boot/recovery image without runtime `memory_give`/`roles::rebuild` across unrelated domains.
- **Removed contract lines & states:** Cuts `core_place` dynamic relocation (`kernel-interface.md:1194`), `role_claim`/`role_hand` runtime bounce (`roles.rs`), `admitted` global budget sum (`table.rs:212`), `core_beacons`/`core_idle` work stealing, and `UnitRequest` forwarding (assign devices statically per driver node).
- **New costs & when paid:** Fixed RAM headroom per static domain; reboot/reset cost (`ms` scale) **paid only on core failure**.
- **Unserved user/app needs:** Dynamic core repacking (hot-scaling a compilation or inference job from 1 core to 16 cores at runtime) and dynamic driver migration across cores.
- **What to measure:** Whether real desktop + agent workloads (UI + browser + local LLM + storage) fit fixed core budgets vs dynamic core scaling on 14–16 core laptops/desktops.

### Option C: Single Owner + Remote Names Without Cross-Node Grant/Revoke State Machines
- **Design:** Keep local capabilities strictly single-core; cross-core IPC uses explicit **non-delegatable ring handles** (`RemoteRef` pointing only to an endpoint/notify or `2 MB` frame slice owned by core `X`). Only core `X` holds the capability tree; core `Y` holds a typed descriptor checked by `(X, X_gen, slot, epoch)`—and core `Y` **cannot** derive or sub-grant it further (`cap_derive` / `send` across nodes forbidden).
- **Removed contract lines & states:** Cuts `Revoke`, `RevokeStep`, `Release`, `pinned` (`R3`), `GRANTS` (`4096 × 128 B = 512 KB/node`), `uses` (`128 KB/node`), `TransferAsk`/`Grant`/`Refused`/`Returned` (`80%` of `remote.rs` complexity and the #1 source of R6/R7 bugs).
- **New costs & when paid:** Forwarding a capability from `Y` to `Z` requires an explicit user-space RPC to owner `X` (`paid only on cross-core capability sharing`, rare event).
- **Unserved user/app needs:** Delegating capabilities received from another core recursively (`X -> Y -> Z`) without contacting `X`.
- **What to measure:** Fraction of real user-space capability transfers in DodOS's hosted userland that pass more than 1 hop across cores.

### Option D: Smaller Op Set (Data-Only Cross-Core Rings + Frame Mapping Only)
- **Design:** Allow only two cross-node primitives in the kernel: (1) `Notify` signal (single atomic cache-line/IPI wake via doorbell) and (2) `2 MB` chunk ownership + read/write `Frame` mapping (`memory_take`/`give`). Cross-core synchronous `Call`, `ReplyRecv`, `SchedBind`, `CSpace` mutation, and `thread_move` are removed; multi-core processes (`Ladybird`, `llama.cpp`) run strictly on `1`-node clusters or multiple instances over shared `Frame` rings.
- **Removed contract lines & states:** Cuts `Request`/`Answer`/`Cancel`, `Transfer*`, `Revoke*`, `Move`/`Moved`, `Carry*`, `PROXIES_PER_PEER`, and remote syscall marshaling in `remote.rs:246–330` and `lib.rs`.
- **New costs & when paid:** Zero runtime overhead on local syscalls; `a3n` atomic `OR` doorbell + `1` batch IPI beats `Candidate 3` (`results-mac-m5.md` Series 4).
- **Unserved user/app needs:** Cross-core synchronous IPC (`call`/`reply_recv`) and transparent remote object manipulation.
- **What to measure:** Latency of `Frame`-ring batched RPC vs kernel `Body::Request` across 2 L3 clusters on Raptor Lake.

### Option E: Replicated State Log + Deterministic Epoch Quorum (NrOS Pattern for Shared Metadata)
- **Design:** Replace the 18 ad-hoc messages + 7-phase `R0–R6` barrier choreography (`recovery.rs`) + `roles::rebuild` with a single **bounded shared ring log** (using `Table` single-writer slots + monotonic log entries) over `(chunks, roles, devices, identifiers)`. Nodes advance an epoch counter synchronously (`quorum` or `live` bitmap) instead of exchanging asynchronous `UnitRequest`, `Handed`, `RevokeStep`, and `Release` replies.
- **Removed contract lines & states:** Cuts pairwise `Transfer*`, `Revoke*`, `Handed`, `UnitRequest`/`UnitAnswer` retry state machines, and `R1`–`R5` interleaved partial state (`roles.rs`, `recovery.rs:480–900`).
- **New costs & when paid:** Memory for fixed-size static ring log (`~64–256 KB` shared across machine); log-apply pause **paid only on rare ownership/role/crash transitions** (matches NrOS read scaling).
- **Unserved user/app needs:** Point-to-point uncoordinated capability cascades that mutate faster than a log epoch.
- **What to measure:** Worst-case log commit latency on `64` cores during `memory_give` / crash reclaim.

### Novel Alternatives

- **Novel proposal 1: Epoch-Stamped Grant Validation + Tombstone Epoch Bump (Eliminates `Revoke`/`RevokeStep`/`Release`/`pinned`).**
  - **Design:** Instead of maintaining distributed `RevokeStep` / `Release` / `R3 pinned` protocols to confirm every grantee has dropped a grant before clearing it, attach a monotonic `rev_epoch: u32` inside each owner's read-only `GrantEntry` alongside `GateWord` validation. To revoke across cores, owner `X` bumps `grant.rev_epoch` (1 gate write), sends 1 doorbell/TLB flush notice (`epoch_barrier`), and waits only for each live core's **single global `flush_epoch` word** (`G12`, already required by `gate-page-tables.md:240–243`!) to pass `rev_epoch`. Any stale remote use or `Body::Request` carrying an older `rev_epoch` fails `O(1)` at validation without `RevokeStep` or `Release` messages!
  - **Removed contract lines & states:** Deletes `Revoke`, `RevokeStep`, `Release`, `Wait::Node` revocation chains, `R3 unpin()`, `GRANTS` back-pointers, and fixes `challenge_breaks.rs` tests #2, #3, #7 by construction.
  - **New costs & when paid:** One atomic read of `(owner, gen, rev_epoch)` on remote grant map + one global `flush_epoch` sweep **paid only on cross-core revoke/give (rare event)**.
  - **Unserved needs:** Fine-grained sub-grant partial revocation (user must allocate separate grant slots per revocable capability).
  - **Measure:** Cross-core `flush_epoch` sweep latency (`tlb_shootdown` + `1` IPI) on 8–16 x86-64 cores vs `RevokeStep`/`Release` round-trips.

- **Novel proposal 2: Thin Static Stage-2 Cluster Monitors + No Runtime `core_place` / Co-Hosted Sealing.**
  - **Design:** Adopt the thin hypervisor monitor (`fencing-without-cooperation.md` Family A) **strictly for physical hardware isolation** (`EPT`/`NPT`/`stage-2` with `2 MB` blocks + x2APIC ICR / `GIC` / `IOMMU` trap), **drop** `core_place` live node-to-core relocation, co-hosted `Sealed` execution, and bare-metal `INIT`/SDEI/custom SBI fencing (`FENCE_CLASS_SIGNALLED` / `MASKABLE`), and bind `1` physical core per fixed kernel node (or `2–4` cores sharing an L3 domain). On failure, the monitor clears stage-2 root + IOMMU context cleanly in `< 50 µs` (`Quest-V` hypercall baseline `497–961` cycles) without touching peer OS cores or `SETTLE_NS = 1 ms` guesses.
  - **Removed contract lines & states:** Deletes `core_place`, `Sealed` co-hosting (`line 1194`), `placed` map (`table.rs:195`), `FENCE_CLASS_*` branching (`kernel-interface.md:1075–1095`), x86 `<1 MB` park stubs, ARM64 SDEI/`CPU_OFF` dance, RISC-V `fence_hart`, and fixes `challenge_breaks.rs` tests #6 and #8 by construction.
  - **New costs & when paid:** Two-stage TLB walk (`-0.6%` to `+7%` on `2 MB` stage-2 pages per `fencing-without-cooperation.md:31, 179`), `+1` hypercall on `2 MB` chunk `memory_take`/`give` (`500–961` cycles, rare event).
  - **Unserved needs:** Zero-hypervisor bare-metal execution (`nested virtualisation` needed for hypervisor apps) and live core migration under `Sealed`.
  - **Measure:** Native vs thin-monitor `2 MB`-EPT `graph500` / browser / `wasi:http` overhead on the reference Intel i5-14600KF.

## 6. Ranked Decisions, 3 Fastest Experiments, and Verdict

### Ranked List (`Keep` / `Change` / `Cut`)
1. **Cut:** Cross-node `cap_derive`, `cap_move`, `untyped_retype`, recursive grant delegation, and `RevokeStep`/`Release`/`pinned` state machines (**cut** in favor of Option C or Novel Proposal 1 epoch stamps; eliminates `~48%` of multi-core bugs).
2. **Cut:** Co-hosted `Sealed` execution + live `core_place` migration + speculative `core_idle` ring work stealing (`Carry`/`Ping`) + unratified bare-metal fencing (`INIT` below `1 MB`, EL1 SDEI, custom RISC-V `fence_hart`).
3. **Change:** Move **process/address-space coordination** to `Candidate 3` (fine-grained per-range/per-endpoint locks + lock-free seqlock slot reads inside a multi-core domain, OR `1` core per node with **Option A/D** data-only rings + `2 MB` chunk ownership) rather than mixing a shared-everything `Table` with 18 ad-hoc inter-kernel RPCs.
4. **Change:** Replace `Table` per-ID `Owner::Node(x)` checks (`table.identifiers`, `table.devices`, `table.chunks`) with `(node, generation)` checks cleared automatically on `Dead` / `CORE_START_FRESH` (`Argon 1.1` / `Opus S1–S2` fix).
5. **Change:** Enforce **global causal / epoch validation** (`serial` + `rev_epoch` + `ObjectKind`) on every cross-node packet (`Move`, `Request`, `UnitRequest`), not merely FIFO ring delivery.
6. **Keep:** **1 kernel per core / per L3 cluster**, **no kernel heap**, **`2 MB` fixed chunk ownership (`owners`)**, **IOMMU per driver**, and **user-space policy** (scheduler/memory placement outside kernel).
7. **Keep:** **Single-core restart without machine reboot**, **only if** backed by either a thin stage-2 monitor (`Novel Proposal 2`) or fixed static partitions (`Option B`) rather than cooperative bare-metal `INIT`/SDEI guessing.

### 3 Fastest Experiments / Models (1–2 Days Each)
1. **Test Novel Proposal 1 (`epoch`-stamped grants) in `dodos-model`:** Replace `RevokeStep`/`Release`/`pinned` and add `(serial, rev_epoch)` checks to `Body::Move`/`Request`/`UnitRequest`; re-run `dodos-model` + [`challenge_breaks.rs`](file:///Users/btw/.t3/userdata/providers/antigravity/3ee7deb29a315284788021b40513bfa34546a79204bcbe2cc59c23215eb83836/antigravity-acp/brain/66f45d7e-bd92-44f2-b987-f23583dce18e/scratch/dodos-challenge/model/tests/challenge_breaks.rs) (`8` tests) under adversarial ring reordering + `Sealed`/crash injection to verify whether the whole `remote.rs`/`recovery.rs` bug cluster disappears.
2. **Prototype x86-64 `WRSSQ` write-gate + `CR3`/thin-monitor EPT overhead on bare-metal i5-14600KF:** Measure `WRSSQ` + `INVPCID` vs `MOV CR3` gate vs `2 MB` EPT hypercall (`500` lines of Rust/asm) on `aspace_map`/`unmap` (`512`-entry batch) and real cross-core IPI latency (`ipi` in `trials/multicore` is currently guessed at `0` or `1 µs`).
3. **Re-run `trials/multicore` (`f9933bd`) on Linux x86-64 (pinned cores, no M5 E-cores) adding subtree-revoke lock contention and atomic-OR `notify`:** Resolves whether `Candidate 3` (fine locks + seqlock) keeps its `27–32%` `a1t` / `1.5×` `br` lead when real `IPI` (`InvPG` + `APIC ICR`), `subtree revoke`, and multi-CCD cache bounces replace Mac M5 guesses.

### 10-Line Verdict
1. DodOS's multi-core design pays the verification, memory, and latency tax of a full distributed capability OS while keeping 18 globally shared mutable kernel tables in `table.rs`.
2. Over 80% of all confirmed Round 6–7 bugs sit in cross-node protocols (`remote.rs`, `recovery.rs`, `roles.rs`, `moves.rs`) and global `Table` ownership/gate tracking—including 3 newly proven crash/isolation bugs in `challenge_breaks.rs` (`8/8` passing across `4k`/`16k`/`32k`).
3. Even strict FIFO ring delivery fails: cross-node reuse of grants without serials and epochs breaks Invariant 58, forges signals onto third nodes, and hangs callers forever.
4. Bare-metal recovery assumes unshipped or contradictory hardware behavior (`SETTLE_NS = 1 ms`, BSP `INIT`/SIPI, EL1 SDEI, custom RISC-V `fence_hart`), while co-hosted `Sealed` execution repeatedly breaks isolation.
5. Real applications get little from this complexity: WASI 0.3.0 has no threads, and native multi-threaded apps (`Ladybird`, `llama.cpp`) still have no multi-node address spaces (`D-027` deferred).
6. In `trials/multicore`, a fine-locked shared kernel with lock-free slot reads beats per-core messaging by 27–32% on 10%-write workloads, 2.3–9.6× on capability edits, and 1.44–2.01× on multi-core unmaps, while matching IPC within 1–2%.
7. Cutting cross-node `cap_derive`, `cap_move`, `RevokeStep`/`Release`, `thread_move`, `core_idle` stealing, and co-hosted `Sealed` removes ~80% of the kernel's protocol state machine without hurting Wasm apps.
8. Replacing multi-step revocation with epoch-stamped grants (`rev_epoch` + `flush_epoch`) closes the stale-message/hang bug class structurally.
9. Replacing bare-metal `INIT`/SDEI guessing with either static core partitions or a thin `2 MB` stage-2 monitor buys genuine fault containment that hardware actually supports.
10. Keep `1` kernel per core/cluster, `no kernel heap`, `2 MB` chunk ownership, and `IOMMU` isolation; cut the distributed capability/role choreography before writing the bare-metal kernel.
