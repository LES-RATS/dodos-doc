# Kernel Shape Design: A Critique of Elastic Kernels and a Proposal for Pruned Per-Core Kernels (Shape D)

- **Author:** gemini-4-hydrogen (design sub-agent)
- **Baseline:** [`Docs/architecture/kernel-interface.md`](/Users/btw/Documents/repos/Docs/architecture/kernel-interface.md) (`3bc7597` / `4b12baf`), [`Docs/architecture/kernel.md`](/Users/btw/Documents/repos/Docs/architecture/kernel.md), [`Docs/decisions/README.md`](/Users/btw/Documents/repos/Docs/decisions/README.md) (`D-001`–`D-124`), `dodos-kernel` branch `model` (`2afc901`) and branch `trial-multicore` (`trials/multicore/results-mac-m5.md`).

## 1. Executive Verdict

**Recommend Shape D: Pruned Lock-Free Per-Core Kernels with Run-Grants, Lazy Aspace Sync, Stateless Signal Grants, Credit-Bounded Stamped Send, and In-Place Core Sleep.**

Shape D keeps one lock-free kernel per physical core (`1` core = `1` node = `1` failure domain), removes all cross-kernel synchronous proxies (`PROXIES_PER_PEER = 16`), `thread_move` (`Move`/`Moved`), `Carry`/`CarryDone`, and D-108 cross-core node parking (`save_seal`, `host` accusation, kernel block migration), while keeping three surgical kernel-enforced cross-core mechanisms:

1. ***Run-Grants* (novel extension of `G6`):** one grant entry covers a contiguous run of chunks rather than one `frame`, collapsing a 4 GiB × 16-core shared heap from `30,720` grants (`> GRANTS = 4096`, [`abi/src/machine.rs:101`](/Users/btw/Documents/repos/dodos-kernel/abi/src/machine.rs)) to `60` grants while preserving two-phase `Revoke`/`RevokeStep`/`Release` and `R3` DMA pinning.
2. ***Stateless `Signal` Grants* (novel capability-generation check):** cross-core `notify` rights are checked against a per-node notify-generation/serial array in the machine table so `signal` is one lock-free ring write and revocation is one local serial increment without `RevokeStep`/`Release` or `pinned` entries.
3. ***Lazy `aspace` Addition + Synchronous Batched Unmap/Protect* (`Adds::Lazy` in kernel):** retains kernel `aspace` coherence (unlike Shape B's user-space double-hop), resolves new mappings in-kernel on minor peer fault (zero user-visible fault per [`kernel-interface.md:318`](/Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L318)), and runs synchronous two-phase invalidation only on unmap/protect/destruction.

**Why the owner's hint (Shape C, elastic kernels) loses:** Elastic kernels pay **twice**. Because drivers are separate processes ([`drivers.md:5`](/Users/btw/Documents/repos/Docs/architecture/drivers.md#L5), D-113), supervisor/memory replicas sit on distinct reserve nodes ([`kernel.md:49`](/Users/btw/Documents/repos/Docs/architecture/kernel.md#L49)), and **WASI 0.3.0 has no threads** ([`wasm-abi.md:128`](/Users/btw/Documents/repos/Docs/architecture/wasm-abi.md#L128) — Wasm parallelism uses separate component instances), Shape C still needs cross-kernel `Send`, `Signal`, grants, membership, fencing, reclaim, and roles. Adding shared-kernel locks and dynamic core attach/detach on top breaks `D-042` (bounded syscalls: M5's `br` explicit gap at [`results-mac-m5.md:971-978`](/Users/btw/Documents/repos/dodos-kernel) leaves table frees and unbounded derivation-subtree `cap_revoke` unverified and deadlocked in lock ordering), breaks Verus sequential gate proofs ([`gate-page-tables.md:602`](/Users/btw/Documents/repos/Docs/research/drafts/gate-page-tables.md#L602)), amplifies crash blast radius to all `m` cores of a group (breaking 2-core survival when `m = 2`), and loses on common-path lookups, IPC, and signals in M5.

**Why Shapes B and A lose:** Shape B pushes multi-core `aspace` management into user agents, paying double ring crossings and priority inversion while still hitting `GRANTS = 4096` (`P1`). Shape A (repaired contract) keeps 6 complex Rule-7 protocols (`18` `Body` variants in [`model/src/remote.rs:37-138`](/Users/btw/Documents/repos/dodos-kernel/model/src/remote.rs)), D-108 parked-node recovery hazards, proxy starvation (`PROXIES_PER_PEER = 16`), and eager map broadcasts (`Adds::Eager`).

> **Novel / Untried Marker:** Cross-core *Run-Grants* spanning arbitrary chunk runs under single-writer CAS gates, *Stateless `Signal` Grants* via read-only generation tables, and *In-Kernel `Adds::Lazy` Fault Sync* between independent per-core page-table copies are **novel combinations** in DodOS (not implemented in `dodos-kernel` `model` or tested on x86-64). They are explicitly marked as unverified prototypes in Section 4.

## 2. The Four Candidate Shapes

| Aspect | Shape A: Repaired Contract | Shape B: Per-Core + User Agents | Shape C: Elastic Kernels | Shape D: Pruned Per-Core (Recommended) |
|---|---|---|---|---|
| **Cores per kernel** | `1` kernel per node; D-108 parks idle nodes onto awake cores (`kernel-interface.md:1090`) | `1` kernel per physical core; no D-108 parking | Dynamic set `1..N` cores per kernel; cores join/leave statelessly (`kernel.md:57`) | `1` kernel per physical core; no D-108 parking |
| **Intra-kernel sync** | None (lock-free, interrupts off) | None (lock-free, interrupts off) | Queue/range locks + `G12` gate lock + per-core flush epochs (`kernel-interface.md:896`) | None (lock-free, interrupts off) |
| **Inter-kernel IPC / calls** | Full Rule 7 (`18` `Body` variants, `PROXIES_PER_PEER = 16`) with uniform `SenderCheck` & FIFO ring order fixed | Only `signal`, `stamped send`, `frame grants`, failure/roles; all RPC/calls in user runtime | Reduced set between kernels; synchronous `Call`/shared `aspace` inside same kernel | Credit-bounded `Stamped Send` (≤ 4 inline grants), `Stateless Signal`, `Run-Grants`, `Adds::Lazy` + `Invalidate`, roles/fencing |
| **Cross-core `aspace` & TLB** | Unwritten group protocol (`kernel-interface.md:320, 1877`) + per-node `aspace` copies | Per-core user memory agents coordinate `frame` grants + IPI shootdown via `Signal` | Shared page tables inside kernel (`Unmaps::Range` locks + local/group TLBI) | Home `aspace` + peer kernel copies (`Adds::Lazy` minor-fault resolve; sync `AspaceInvalidate` on unmap/protect) |
| **Thread migration** | `thread_move` (`Move`/`Moved`) + D-108 `core_place` | User-level checkpoint/spawn (`thread_read_regs`/`write_regs`) | Thread scheduler lock within kernel; cross-kernel spawn via user space | User-level suspend + `thread_read_regs`/`write_regs` (`REGS_WORDS = 26`) + destination setup |
| **Failure & recovery unit** | `1` node (`m` nodes if co-hosted on 1 dying core) | `1` core (`1` kernel) | `m`-core kernel (kills all `m` cores & all co-hosted apps on 1 kernel bug) | `1` core (`1` kernel) |

## 3. Concrete Walkthrough of Cases 1–8 Across Shapes A, B, C, and D

### Case 1: 16-Thread Wasm/Native Process (1 Address Space; Map, Unmap, Protect, TLB; Grow `1 → 16` Cores and Shrink)

First, note a fixed fact from [`wasm-abi.md:128`](/Users/btw/Documents/repos/Docs/architecture/wasm-abi.md#L128): **WASI 0.3.0 has no threads**. Wasm applications scale by running independent component instances (separate address spaces), so the multi-threaded 16-core shared-`aspace` stress case applies to native services and runtimes (Ladybird, inference, or future `shared-everything-threads` Wasm).

- **Shape A:**
  - *State & Ownership:* Home node `H` owns the process memory chunks and home `aspace`. Each of `15` peer nodes (`1..15`) holds a peer `aspace` copy paid from chunks moved to that node, mapping the process's frames via `1` `Frame` grant per `2 MiB` frame (`kernel-interface.md:320`).
  - *Arithmetic Failure (`P1`):* A `4 GiB` heap split into `2,048 × 2 MiB` frames mapped on `16` nodes consumes `2,048 × 15 = 30,720` grant entries on `H`, overflowing `GRANTS = 4096` ([`abi/src/machine.rs:101`](/Users/btw/Documents/repos/dodos-kernel/abi/src/machine.rs)) by `7.5×`.
  - *Messages & TLB:* `aspace_map`, `aspace_unmap`, `aspace_protect`, and record deletion broadcast to all `15` peers, block caller in `Wait::Node` (`Adds::Eager`, unwritten at `kernel-interface.md:1877`), and wait for `15` acks. Growth `1 → 16` executes `15 × thread_move` (`Move`/`Moved`) and `15 ×` peer `aspace` builds; shrink uses `core_stop(seal)` / `cap_delete`.
  - *Crash at any step:* If `H` dies, the entire process dies (`kernel.md:48`); peers destroy copies in `R2` (`kernel-interface.md:1103`). If peer `P_i` dies during unmap, `R0` wakes `H` with `gone` (`:1098`), `R3` pins `H`'s grants to `P_i` until `P_i` is dead, and `P_i`'s threads are lost while the rest survive.
- **Shape B:**
  - *State & Ownership:* `16` independent user-space memory agents (one per core) hold local `aspace` and `frame` grants from `H`.
  - *Messages & TLB:* Map/unmap/protect goes from thread → local agent (IPC) → `H`'s agent (`Stamped Send`) → `15` peer agents (`Stamped Send`) → each peer kernel (`aspace_unmap`) → local `INVLPG`/`TLBI` → ack (`Signal`/`Send`) → caller. Every unmap adds extra user-mode scheduling delays (if a peer core runs a `Frame`-class thread, a `Background`-class memory agent is delayed until replenishment or slack). Still hits `P1` (`30,720 > 4,096`) because `GRANTS` counts single `Frame` caps.
  - *Crash at any step:* Same survival boundary (`H` fatal, `P_i` partial loss); an unmap stuck waiting on a dead user agent needs a lease timeout or `core_watch` death notification wired to every user memory agent.
- **Shape C:**
  - *State & Ownership:* One `16`-core kernel holds `1` shared `aspace` (no duplicate page tables, `0` grants for that process) guarded by `Unmaps::Range` locks (or whole-`aspace` lock for subtree `cap_revoke`), plus a `G12` gate lock and per-core flush epochs (`kernel-interface.md:896`).
  - *Growth `1 → 16` & Shrink:* Adding a core requires parking/handing off any prior kernel on that core, draining its rings/roles, flushing local state, and inserting the core into kernel `K`'s IPI mask and `G12` epoch array. Shrinking requires draining the departing core's `G12` epoch and migrating any thread/IRQ pinned there.
  - *Map/Unmap/TLB:* Map/protect/unmap takes the range lock + `G12` gate lock, writes shared PTEs once, sends targeted IPIs to active cores of the process, spins on acks (`TLB` shootdown), and releases locks.
  - *Unbounded `D-042` Failure:* As [`results-mac-m5.md:971-978`](/Users/btw/Documents/repos/dodos-kernel) admits, freeing page tables or running `cap_revoke` across ranges/aspaces cannot use per-range locks safely without whole-space locking or unresolved lock-order protocols. And if *any* one of the `16` cores hits a kernel panic, **all 16 cores and every other process co-hosted on them die at once**.
- **Shape D:**
  - *State & Ownership:* Home node `H` owns memory chunks and the authoritative `aspace`. Peer nodes (`1..15`) hold `Run-Grant` entries (up to `E` chunks per entry, so a `4 GiB` heap uses at most `4 × 15 = 60` grants on `H` and `4` `UseEntry` slots on each peer). Each peer holds a lazy kernel-managed `aspace` replica populated from `H`'s home `aspace` descriptor/slot through the gate.
  - *Map (`Adds::Lazy`, novel):* `H` inserts the mapping into `H`'s `aspace` (updating `H`'s `GateWord` map count), bumps `aspace.map_epoch`, and sends **zero IPIs**. When a thread on peer `P_i` touches the newly mapped page, `P_i` takes a kernel-handled minor page fault: `P_i`'s kernel checks the `Run-Grant` + `H`'s read-only home `aspace` slot (or `AspaceFetch` message to `H`), installs the leaf through `P_i`'s gate (counting in `P_i`'s `UseEntry`), and resumes the user thread transparently (matching `:318`).
  - *Unmap / Protect:* `H` updates its copy, marks the mapping revoking/updating, and sends batched `AspaceInvalidate(aspace_gen, seq, addr, pages)` messages only to peers whose `active_aspaces` bit for that space is set, waiting for `AspaceAck`. Each peer unmaps locally, issues local `INVLPG`/`INVPCID` (x86-64) or local `TLBI VALE1` (`CnP=0`, Arm DDI 0487 per [`verify-opus-by-hydrogen.md:115`](/Users/btw/Documents/repos/Docs/reviews/2026-11-16-verify-multicore-challenge-opus-by-hydrogen.md#L115)) or `SFENCE.VMA`, and emits `AspaceAck`.
  - *Growth `1 → 16` & Shrink:* User placement service creates threads on target cores bound to peer `aspace` replicas (`AspaceJoin` lazy attach via `Run-Grant` passed inline in startup `Stamped Send`) and migrates suspended thread register state via `thread_read_regs`/`thread_write_regs` (`REGS_WORDS = 26`). Shrinking sends `AspaceLeave` to drop peer replica and `Release`s the `Run-Grant`.
  - *Crash at any step:* If `H` dies, `R0` immediately terminates any waiting `AspaceFetch`/`AspaceInvalidate` on peers with `gone`, and `R2` tears down peer copies cleanly. If `P_i` dies mid-`AspaceInvalidate`, `R0` immediately wakes `H` (`gone`) without waiting for `P_i`'s `AspaceAck`, `R3` pins the `Run-Grant` until `P_i` is dead (protecting DMA/stale translations), and survivors continue (`liveness.rs` invariants hold).

### Case 2: Client and Service on Different Kernels (Call, Reply, Capability Hand-Over, Revocation)

- **Shape A:** Client calls remote `endpoint` → allocates 1 of `PROXIES_PER_PEER = 16` (`abi/src/machine.rs:209`), sends `Request`, enters `Wait::Node`. Reply takes `Answer`. Capability argument triggers `TransferAsk` → `TransferGrant` (`Crossing::Grant`/`Home`) → `Refused`/`Returned`. Revocation runs multi-step `Revoke` → `RevokeStep` → `Release` (plus `pinned` if grantee fencing). **Flaw:** `16` idle waits freeze unrelated `Send` and `Signal` on the same peer (`verify-opus-by-hydrogen.md:104-105`), and `CapDelete` of a CSpace with `33` remote notifies emits `32` `Release` packets in one syscall (`:109`).
- **Shape B:** Kernel provides only `Stamped Send` + `Signal` + `Frame` grants. Client user runtime writes RPC payload to shared ring (under `Frame` grant) and calls `Signal` or `Stamped Send`; server replies on reverse ring + `Signal`. Hand-over of *non-frame* capabilities (`endpoint`, `task`) cannot use kernel grants—user space must build a broker/proxy protocol in user space. `Frame` grant revocation still uses kernel `Revoke`/`RevokeStep`/`Release` bounded by `GRANTS = 4096`.
- **Shape C:** If client and service share a kernel, `call`/`reply_recv` takes a per-endpoint lock (`1–2` cache lines), checks derivation, swaps threads locally, and lends budget. If they lie on **different** kernels (e.g., driver in separate kernel, system service on reserve node), Shape C falls back to the exact reduced cross-kernel protocol of Shape B. Thus Shape C needs **two complete RPC & capability paths** (intra-kernel locked + inter-kernel async).
- **Shape D:**
  - *Call & Reply:* Cross-core synchronous kernel `call` is removed (`call`/`recv`/`reply_recv` are strictly **local** to one node, keeping the fast register switch and MCS budget lend inside 1 core without `Proxy` starvation). Across kernels, the user-space WASI/WIT async runtime copies control words into a pre-shared `Run-Grant` ring or issues credit-bounded `Stamped Send` (carrying unforgeable `(from_node, from_gen, task_id, effective_marks)`), paired with `Stateless Signal` for wake-up.
  - *Capability Hand-Over:* Only `Frame` (`Run-Grant`), `Notify` (`Stateless Signal` token), and `Device` capabilities cross kernels. If handed inline in a `Stamped Send` (`≤ 4` items, pre-allocated ring credit guarantees room), the sender's gate writes the `GrantEntry` (for `Run-Grant`) or mints a `(node, gen, notify_id, badge, serial)` token (for `Stateless Signal`) *before* enqueueing; the receiver installs the `UseEntry`/slot atomically on dequeue (`TransferAsk`/`Refused` eliminated).
  - *Revocation:* Revoking a `Run-Grant` runs bounded `Revoke` → `RevokeStep` → `Release` (`R3` pinning if grantee dies). Revoking a `Stateless Signal` bumps that `notify`'s 32-bit `serial` locally in the machine table in **one write** (instant `gone` on every remote sender; `0` messages, `0` `Release` packets, resolving the `32`-release burst of [`verify-opus-by-hydrogen.md:109`](/Users/btw/Documents/repos/Docs/reviews/2026-11-16-verify-multicore-challenge-opus-by-hydrogen.md#L109)).
  - *Crash at any step:* No remote `Proxy` exists to orphan; `R0` discards queued `Stamped Send`s from a fencing sender; a crashed grantee leaves `Run-Grant` pinned until dead (`R3`); a crashed client leaves the server runnable on its own context (no cross-core MCS lend deadlock).

### Case 3: Driver (Interrupts, IOMMU, Clients on Other Kernels)

Under [`drivers.md:5,58`](/Users/btw/Documents/repos/Docs/architecture/drivers.md#L5), each driver is a separate user process whose `iospace`, device MMIO `frame`s, and `irq`s belong to its node (`D-113`), while shared IOMMU/IOAPIC/ITS/APLIC hardware is serialized by unit **Roles** (`kernel-interface.md:1200`).

- **Shape A:** Driver runs on node `D`, unit role on node `R`, clients on nodes `C_i`. IRQs deliver straight to `D` (`irq_ack` local; level EOI via IOAPIC EOI register, `:866`). `iospace_attach`/`iospace_unmap` send `UnitRequest(epoch)` to `R` (`Wait::Node`). Clients share DMA buffer `Frame` grants from `C_i` (hitting `P1` on big buffer pools) or `D`.
- **Shape B:** Same role-holder split for IOMMU/IOAPIC (roles are in the fixed machine table), except if `iospace_attach`/`unmap` loses Rule-7 `UnitRequest` proxy blocking, a user agent on `D` must poll or wait via `Stamped Send` + `Signal` to `R`'s kernel role stub, adding latency and trusting `D`'s user agent on fault paths.
- **Shape C:** If `D` and `R` are merged into one kernel, `UnitRequest` is skipped via a lock, **unless** `D` and a client `C_i` or `R` are in separate elastic kernels (e.g., fault containment per [`drivers.md:5`](/Users/btw/Documents/repos/Docs/architecture/drivers.md#L5)), where Shape C still pays cross-kernel unit requests. Worse, co-hosting a heavy/buggy driver kernel with other cores expands a driver-kernel crash to all cores in that elastic kernel.
- **Shape D:** Keeps the exact `D-113` / [`kernel-interface.md:864-866`](/Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L864-L866) split:
  - *Interrupts:* Device MSI/MSI-X routes directly via interrupt-remapping entry (`node * 192 .. +191`, `:864`) to `D`'s core; `irq_ack` and `notify` wake-up are 100% local.
  - *IOMMU:* `iospace_map` is local if caching-mode = 0 (`:864`); `iospace_attach`/`unmap` send asynchronous `UnitRequest(epoch)` to `R`'s recovery/role handler (kept outside the removed IPC `Proxy` pool — a tiny fixed 1-slot-per-node role mailbox, no `PROXIES_PER_PEER = 16` starvation!).
  - *Clients on other kernels:* Share zero-copy sDDF-style rings (`drivers.md:16`) over `Run-Grant`s (1 grant per buffer pool instead of 1 per `2 MiB` frame!) and wake via `Stateless Signal` (which batches interrupts on busy receivers, matching M5 `a3t`: `4.42M` signals/s at `k=8, W=200ns, ipi=1µs`, [`results-mac-m5.md:803`](/Users/btw/Documents/repos/dodos-kernel)).
  - *Crash:* If `R` dies, `R1` runs on successor `S` (`R1` clears `R`'s device contexts, rebuilds live/sealed nodes' contexts, and sets `acked`, fixing the `roles::rebuild` bug in [`verify-hydrogen-by-opus.md:120`](/Users/btw/Documents/repos/Docs/reviews/2026-11-16-verify-multicore-challenge-hydrogen-by-opus.md#L120)), while running drivers (`D`) keep doing DMA/MMIO/IRQs uninterrupted (`:866`). If `D` dies, `R1` blocks `D`'s devices immediately (`:1099`), `R3` pins client `Run-Grant`s until `D` is dead, and survivors never hang.

### Case 4: Idle Machine (Which Cores Sleep, Who Holds What They Held, Waking)

- **Shape A (D-108):** Idle nodes call `core_stop(seal)` and `core_place` onto one awake core `A` that multiplexes their node blocks (`kernel-interface.md:43, 1090`), while emptied physical cores park (`CORE_STATUS_PARKED`). **Fatal complexity:** Review rounds 6 & 7 and `verify-hydrogen-by-opus.md:70,115-120` proved D-108 co-hosting is a repeat source of bugs (`roles::rebuild` erasing sealed IOMMU entries, ARM64 `ParkSelf` self-kill wedging in `Unfenced`, `host` accusation destroying co-hosted live nodes, `save_seal` races, and unmeasured 20 ms switch overheads cited from Barrelfish/DC).
- **Shape B & Shape D (In-Place Deep Sleep, NO D-108 Parking):**
  - *Which cores sleep:* Every core with no eligible runnable context enters its deepest firmware idle state (`MWAIT` / `CPU_SUSPEND` / `sbi_hart_suspend`, `:595, 1188`) whose exit latency fits `idle_until` (next timer/replenishment deadline, `:545`). No periodic tick (`scheduling.md:19`).
  - *Who holds what they held:* Each sleeping core retains its own kernel block, RAM floor/chunks, `Run-Grant`s, and `iospace`s in place. Before entering deep sleep (`C6`+), a node **hands off any Unit Role** (`role_hand`) to an awake core (so IOMMU/IOAPIC changes do not wake it unnecessarily), publishes `idle_until = next_deadline` (or `∞`) in its core beacon (`:1052`), and sleeps. Because of `:1069` ("A node is judged only when someone needs it"), neither the sweep nor survivors wake an idle node unless a peer needs an answer or a long `SWEEP_NS` (`1 s`) check triggers, and `idle_until` prevents false `stale` accusations (`:1063`).
  - *Deep retirement / core offlining:* Only when a core is deliberately retired or hot-swapped (`core_stop(seal)` → `Sealed`), its state freezes on its floor until `core_start(resume)`, while **no other node shares its physical core** (`host` co-hosting complexity = 0).
  - *Waking:* An IPI (`Signal`/`Stamped Send`/`AspaceInvalidate`), local deadline timer, or device MSI wakes the core straight from `MWAIT`/`CPU_SUSPEND` in microseconds without restoring a migrated node block (`core_start(resume)` is not needed on ordinary idle).
- **Shape C:** Either leaves empty cores powered off (shrunk kernel to `1` core — still holding that `1` kernel's state in RAM, identical to D's in-place sleep except C must run a cross-core detach protocol every time a core goes idle and re-attach when load rises!) or parks all `m` cores except `1`, incurring attach/detach IPIs + lock/TLB initialization on every burst.

### Case 5: Performance and Efficiency Cores; 2 Cores; 64 Cores

- **P & E Cores (e.g., Intel Core i5-14600KF: `6P+8E`):**
  - *Shape A:* Per-core kernels naturally match `D-115` / `D-118` (each node publishes core capabilities, ISA features, vector lengths, and `core_perf`; `Frame` class runs on P-cores, `Background` on E-cores, [`scheduling.md:38-41`](/Users/btw/Documents/repos/Docs/architecture/scheduling.md#L38-L41)). Moving threads across unlike cores uses `thread_move` (`Move`/`Moved`).
  - *Shape B & D:* Same clean core-type isolation. Each node runs a homogeneous core; zero cross-core lock inversion. A background E-core throttling or stalling in SMM **never** holds a spinlock needed by a `Frame`-class P-core. In Shape D, migrating a thread from an E-core to a P-core is done explicitly by the user placement service (`thread_suspend`, `thread_read_regs`, `thread_set_features` on compatible target, `thread_write_regs`, `thread_resume`), avoiding kernel `Move`/`Moved` lock-step protocols while preserving `D-118` vector safety.
  - *Shape C:* If an elastic kernel spans both P and E cores, a throttled/clock-gated E-core holding `G12` or `Unmaps::Range` directly stalls a `Frame`-class P-core inside the same kernel (quantified in M5 at `k=8`, where `53%` E-core mix degraded `3`'s locked `a1` lookup `p50` to `7.90–8.06 µs` vs `1.00 µs` in per-core `1`, [`results-mac-m5.md:96,103`](/Users/btw/Documents/repos/dodos-kernel)). If C restricts elastic kernels to single-class islands (only P or only E), C cannot grow a process across P+E or shrink cleanly across them anyway!
- **2 Cores (e.g., minimal embedded / rescue boot):**
  - *Shape A / B / D:* 2 independent nodes (`0` and `1`). Node `0` can recover node `1` (or vice versa) using no-vote evidence (`kernel-interface.md:1073`), because `n - 1 = 1` live survivor always remains (`S7` satisfied).
  - *Shape C:* **Breaks recovery.** If the 2 cores merge into `1` elastic kernel to run a 2-core process, there are `0` surviving kernels if that kernel panics (`core_stop` refuses when no other kernel stays live, `:1181`), violating D-026 ("a kernel that panics restarts alone, and the machine continues"). Keeping 1 core permanently in reserve leaves only 1 core for all work (`50%` hardware wasted).
- **64 Cores:**
  - *Shape A:* `NODES_MAX = 1024`, `acked` takes `8 * 64^2` bytes (`32 KB`; `8 MB` at `1024`, `:1230`), `PROXIES_PER_PEER` takes `64 * 64 * 16 * 1 KB = 64 MB` (`abi/src/machine.rs:209-210`). Map/unmap broadcasts hit `63` IPIs on process-wide address spaces, and `GRANTS = 4096` overflows on large shared heaps (`P1`).
  - *Shape B:* Eliminates `64 MB` proxy tables, but user-level `aspace` coordination across 64 cores suffers multi-hop latency and still hits `GRANTS = 4096`.
  - *Shape C:* A single `64`-core elastic kernel turns into an SMP microkernel lock nightmare: M5 already shows single-lock saturation at `~0.91 M ops/s` (`results-mac-m5.md:80`), and even with range locks, global `cap_revoke` or `G12` flush epochs across 64 cores recreate classic SMP scalability and `D-042` bound failures—while putting all 64 cores in one failure domain.
  - *Shape D:* Scales cleanly at `64` cores: `64` independent lock-free kernels; `0` proxy tables (`64 MB` saved); `Run-Grant` keeps grant tables tiny (`4,096` entries easily cover terabytes of shared chunks); `Adds::Lazy` avoids unnecessary `map` IPIs; `AspaceInvalidate` targets **only** cores in `active_aspaces` bitmask (e.g. `1–16` active cores, not all `64`); and `Stateless Signal` uses `64` small generation tables (`~64 KB` total) with `0` revoke messages.

### Case 6: A Kernel Dies (Lost, Noticed, Fenced on x86-64/ARM64/RISC-V, Duration, What Survivors Never Wait For)

- **Shape A:**
  - *What is lost:* Dying node `X`'s objects (`cspace`, `aspace` home processes, threads, local drivers), **plus** any other node parked on `X`'s core whose `save_seal` was invalid (`host` accusation, `:1067, 1089`).
  - *Notice & Fence:* Detected via `self` (`panic != 0`), `stale` (`STALE_NS = 100 ms`), `stuck` (`STUCK_NS = 100 ms`), `SWEEP_NS` (`1 s`), or `kill`/`retire` (`:1060-1070`). Gate checks evidence, sets `fencing(g)`.
  - *Architecture fencing (`kernel-interface.md:1079-1088`, [`fencing-without-cooperation.md:68-107`](/Users/btw/Documents/repos/Docs/research/drafts/fencing-without-cooperation.md#L68-L107)):*
    - **x86-64:** Step 1 sends `NMI` (`NMI_GRACE_NS = 1 ms`) — exits VMX non-root (`SDM §28.3`), runs after `RSM` (`§34.8`). Step 2 sends `INIT` + `2× SIPI` (`200 µs` apart) to the park stub (except BSP, where `INIT` resets firmware per `Linux e1c467e69040`, and cores in VMX root where `INIT` is blocked per `SDM §28.2`). Confirmed via `parked` epoch or `SETTLE_NS` (`1 ms`) after `INIT` with `vmx == 0`.
    - **ARM64:** Kernel runs at `EL2` (where present, `VHE`). Peer sends `SDEI_EVENT_SIGNAL` (requires `ELD=EL3`, client at highest NS EL per `DEN0054C §3.2.1`, preempts `PSTATE.{A,I,F}`); handler calls `PSCI CPU_OFF` (stops caller only); confirmed by `AFFINITY_INFO == OFF`. If no SDEI or Trusted OS blocks `CPU_OFF`, core is Class 0 (cannot co-exist without hardening monitor, `:1088`).
    - **RISC-V:** Calls custom SBI `fence_hart` (M-mode stops target hart forcibly; standard `sbi_hart_stop` stops only caller). Without `fence_hart`, Class 0 cooperative only.
  - *Duration:* `NMI_GRACE_NS` (`1 ms`) + `INIT/2×SIPI` (`~0.2–1 ms`) + `SETTLE_NS` (`1 ms`) ≈ `2–3 ms` after detection (`100 ms` default `STALE_NS`/`STUCK_NS`), bounded by `FENCE_NS` (`10 ms`) + `R1..R6` in `1/64` recovery reserve (`156 µs / 10 ms`, `:1231-1237`).
  - *Survivors never wait for:* Dying core to release locks, reclaim memory synchronously, or answer calls (`R0` ends all remote waits with `gone`). However, on `unfenced` (BSP NMI failure / ARM64 Class 1 hang), memory & grants stay frozen until reboot (`:1091`), and any co-hosted node on that core gets dragged down.
- **Shape B & Shape D:**
  - *Identical hardware fencing & duration* per core (`1` node = `1` physical core), **except zero co-hosted victims** (`host` disappears) and **smaller `R0..R6` state**: no `Proxy` cleanup needed in `R0` (in D), no `ThreadMove` rollback, no `TransferAsk` rollback.
  - *What survivors never wait for in D:* Survivors never wait for `X` to acknowledge `AspaceInvalidate` (`R0` returns `gone` when `X` enters `Fencing`), never wait for `X` to release `Stateless Signal`s (`0` state held on `X`), never wait for `X` on synchronous `Call`/`Recv`/`Wait` (none cross cores), and `iospace`/driver operations on other nodes never wait for `X` even if `X` held a unit role (unit role rebuilds from live+sealed reports after `SETTLE_NS`, `:1214`).
- **Shape C (Elastic Kernel Dies):**
  - *What is lost:* **Every thread and every local process across all `m` cores** of kernel `K` dies simultaneously (`kernel.md:44, 58`).
  - *Stopping ALL `m` cores (`kernel-interface.md:1079-1088`):* The accuser/driver must sequentially fence **all `m` physical cores** of `K` before `K` can reach `fenced` and before `R2`–`R6` can free shared memory:
    - **x86-64:** If *any 1 of the `m` cores* is the BSP (Class 1) or inside VMX root (`vmx=1`), `INIT` cannot stop that core; if that core's NMI handler fails, **all `m` cores' shared memory and all `m` cores' grants stay frozen `unfenced` until machine reboot**.
    - **ARM64:** Every single core of the `m` cores is Class 1 (`SDEI_EVENT_SIGNAL` + self `PSCI CPU_OFF`). The probability of 1 core failing cooperative `CPU_OFF` scales with `m`, holding the whole `m`-core kernel `unfenced`.
    - **RISC-V:** Requires `m` separate `fence_hart` SBI calls (unless `fence_hart` accepts a hart mask); without `fence_hart`, `m` cores cannot even safely form an elastic group without an HS monitor (`:1088`).
  - *Duration:* `m ×` fencing sequence + `SETTLE_NS` + clearing a larger `m`-core `map_count`/`page_class` footprint in `R6`. Worst of all, **recovery requires >= 1 outside kernel**, so an elastic group of size `N` or `2/2` cannot recover itself.

### Case 7: Kernel Replaced by a New Version While Machine Runs

- **Shape A:** Supervisor calls `core_stop(seal)` → node hands off unit roles, drains/refuses proxies, writes `save_seal`, parks → `core_start(resume, replacement_image)` checks binary format version (`kernel-interface.md:1175`). If format mismatch or D-108 co-hosted fault (`verify-hydrogen-by-opus.md:27` T8 on ARM64!), replacement fails and wedges/restarts.
- **Shape B & Shape D:** Every core replaces **one by one** with zero cross-core lock migration and zero co-hosted blocks:
  1. Supervisor calls `core_stop(X, seal)` (`mode = 1`).
  2. `X` transitions `live → sealing`: drains any in-flight `UnitRequest` and hands off unit roles via `role_hand` (`:1213`).
  3. `X` pauses its `Stamped Send` dequeue, answers no new `AspaceInvalidate` (peer waits briefly or triggers timeout→`fencing` only if `STALE_NS` passes; better: `sealing` node processes pending `AspaceInvalidate` in its last loop before writing `sealed`!), serializes its node block (versioned `abi/` header), writes `save_seal` + `member = sealed(g)`, and halts its core.
  4. Supervisor calls `core_start(X, resume, IMAGE_REPLACEMENT)` from another live core. New kernel validates `save_seal` and node-block version, clears `save_seal`, sets `live(g)`, re-validates `Run-Grant`s against current granting node generations (like `:845` R2 check on resume), and resumes scheduling seamlessly. Inter-kernel protocol is versioned (`kernel.md:32`), and rollback to fresh boot (`core_start(fresh)`) recovers cleanly if format checks fail.
- **Shape C:** Replacing an `m`-core elastic kernel either forces freezing **all `m` cores simultaneously** (halting `m` cores of apps and breaking `Frame`-class deadlines across the whole group!) or requires draining & shrinking the elastic kernel `m → 1` one core at a time before replacing the last core—reintroducing all shrink/migration mechanics just to apply an update.

### Case 8: Supervisor and Memory Service Surviving Any 1 Kernel's Death

- **Shape A / B / D:** Under [`kernel.md:49`](/Users/btw/Documents/repos/Docs/architecture/kernel.md#L49) and [`kernel-interface.md:1216`](/Users/btw/Documents/repos/Docs/architecture/kernel-interface.md#L1216), `RESERVES_MIN = 2` reserve roles (`abi/src/machine.rs:215`) hold dedicated reserve chunks (`reserve_bytes + reserve_per_gib * O`, `:1656`) outside ordinary floors. Two supervisor replicas + two memory-service replicas run on distinct physical cores holding distinct reserve roles and replicated state (over `Stamped Send` + `Run-Grant` shared log / deterministic state machine, never keeping single-replica state, `:1216`).
  - *Survival:* If kernel `0` (holding Reserve 0 and Supervisor Leader plain role) dies:
    1. Kernel `1` (or any survivor) notices via `core_watch(notify)` when kernel `0` enters `fencing`/`fenced`/`dead`.
    2. Once kernel `0` reaches `fenced`, Supervisor Backup on kernel `1` immediately runs `role_claim` on plain role `leader` (`:1207`) and continues orchestrating `R6`/reloads (`core_start(0, fresh)`).
    3. Memory Service Backup on kernel `1` reconstructs authoritative global memory ownership purely by reading slot `13` (living machine table: ownership words + `Run-Grant` tables + `identifier` words, `:813`), never touching kernel `0`'s corruptible private RAM. Once kernel `0` reaches `dead`, Reserve 0's free chunks become reclaimable (`R6`, `:1110`) and a fresh replica starts on kernel `0` (or another live core) via `role_claim(reserve_0)`.
  - *Crucial distinction for Shape D:* In Shape A, a buggy supervisor replica on kernel `0` could stall a remote `call` or co-hosted node before dying; in Shape D, replicas communicate purely via non-blocking `Stamped Send` + `Stateless Signal` + replicated `Run-Grant` buffers, so `R0` breaks zero remote locks/proxies when replica `0` crashes.
- **Shape C:** If both Supervisor or both Memory Service replicas ever accidentally get placed on cores of the **same** elastic kernel (or if `m = N` on a small machine), a single kernel panic wipes out **all replicas at once**, breaking Case 8 completely. Shape C must enforce anti-affinity across elastic kernels, which means supervisor/memory service cores *must* stay partitioned per-core anyway—proving again that elasticity cannot unify the whole machine.

## 4. Deep Dive on Shape D

### 4.1 Complete Cross-Kernel Interface & Protocol State Machines

Everything crossing between two kernels (`node i ≠ node j`) in Shape D falls into **two** planes: (1) **Bounded Lock-Free Message Rings** (`N × N` fixed SPSC rings in kept memory), and (2) **Gated Shared Words** in the living part of the machine table (`slot 13`). There are **only 9 message `Body` variants** (down from `18` in [`model/src/remote.rs:37-138`](/Users/btw/Documents/repos/dodos-kernel/model/src/remote.rs)) and **5 shared word classes**.

#### A. Complete Message Set (`Packet { from: u16, generation: u32, to: u16, body: DBody }`)

Every packet undergoes the **uniform `SenderCheck`** (`member[from]` must be `Starting | Live | Sealing` with `member[from].generation == packet.generation`, plus per-message role/grant-entry authority check) before mutating any state:

| # | `DBody` Variant | Direction & Trigger | Payload & Inline Bound | Protocol States |
|---|---|---|---|---|
| 1 | `StampedSend { tag, words: [u64; 64], task_id, marks, grants: [Option<InlineGrant>; 4] }` | User `send` on `core(to)` with receiver's mailbox badge | Pre-committed `Run-Grant` (`base_chunk, chunk_cnt, rights`) or `StatelessSignal` token (`node, gen, notify_id, serial, badge`). **Credit-bounded:** sender holds per-`(from, to)` ring credit (`RING_SLOTS / N` or fixed `64` slots/pair) | Sender gate allocates `GrantEntry` (for `RunGrant`) *before* ring write → Receiver installs `UseEntry` at delivery, else emits `Release` if receiver died/full (`caps_dropped`) |
| 2 | `StatelessSignal { notify_id, serial, bits }` | User `signal` on remote `Notify` cap (optional batched IPI) | Target `notify_id` (`u32`), expected `serial` (`u32`), `bits` (`u64`) | Sender checks `notify_gen[to][notify_id] == (to_gen, serial)` **before** enqueue (`invalid`/`gone` locally if mismatched!). Receiver checks `(current_gen, notify_serial[notify_id]) == (to_gen, serial)`, atomically ORs `bits` into `notify.word`, wakes local waiter |
| 3 | `Revoke { id, grant, serial }` | `cap_revoke`/`cap_delete` on `RunGrant` anchor | Grant index (`u16`), serial (`u32`) | Grant: `Live → Revoking` (`granter` gate refuses new mappings). Holder: `Idle → Removing` (≤ 32 unmaps/step) |
| 4 | `RevokeStep { id, done }` | Grantee answer per ≤ 32 unmaps | `done: bool` | `done == false`: granter returns `Again`. `done == true`: holder frees `UseEntry`, granter frees `GrantEntry` (`serial += 1`) |
| 5 | `Release { grant, serial }` | Grantee drops `RunGrant` root or refuses `InlineGrant` | Grant index (`u16`), serial (`u32`) | Holder clears `UseEntry` first; Granter validates `(grantee, grantee_gen, serial)` and frees `GrantEntry` (keeping anchor if granter still has local children, `:844`) |
| 6 | `AspaceInvalidate { id, aspace_id, gen, seq, va, pages }` | `aspace_unmap`, `aspace_protect`, or `aspace` destruction on home `H` | Range `[va, va + pages*P)`, monotonic `seq` | Home sets `wait_mask` of active peers → sends to each active peer → Peer unmaps local replica, local TLBI, replies `AspaceAck` (or `R0` ends wait with `gone` if peer enters `Fencing`) |
| 7 | `AspaceAck { id, seq }` | Peer kernel after local unmap + TLBI | Request `id`, `seq` | Home clears peer bit in `wait_mask`; when `wait_mask == 0`, home wakes calling thread (`Done`) |
| 8 | `UnitRequest { id, role, op, epoch }` & `UnitAnswer { id, done }` | `iospace_attach`, `iospace_unmap` (when devices attached), `irq` IOAPIC/ITS map | Fixed 1-outstanding slot per `(requester, role)` (outside IPC pool!) | Requester reads `role[role] == Held(holder, epoch)` → waits in `Wait::Unit`. Holder checks `epoch == current_epoch` (`done = false` on mismatch triggers re-read; `R0` re-targets on `holder` death) |
| 9 | `Handed { role }` & `Ping` | Step 4 of `role_hand`; failure `SWEEP_NS` probe | `role: u16`; empty `Ping` | `Handed`: `RoleState::Handing(X→Y, e+1)` → `Y` runs `R1` for fencing/dead nodes, maps unit, writes `Held(Y, e+2)`. `Ping`: advances ring consumer index to prevent false `stuck` |

*(Note: `TransferAsk`, `TransferGrant`, `Refused`, `Returned`, `Proxy Request/Answer/Cancel`, `Move/Moved`, and `Carry/CarryDone` are **all eliminated**. `core_idle` and `core_perf` move to the node-agent user service via `StampedSend` to slot `15` mailbox, and `AspaceFetch` for `Adds::Lazy` reads the read-only `slot 13` / home `aspace` shadow descriptor through the peer's gate or uses `AspaceFetch`/`AspaceSupply` over the fixed per-node fault ring—zero dynamic allocations.)*

#### B. Shared Words in Machine Table (`slot 13`, Read-Only Outside Write Gate)

1. **`MemberWord[N]` (`64`-bit CAS via Gate):** States `Dead(g) → Starting(g+1) → Live(g) → Sealing(g) → Sealed(g)` or `→ Fencing(g) → Fenced(g) / Unfenced(g) → Dead(g)`. (`Sealed` reachable only from `Sealing` when single-core stop is clean; no `host` transition!)
2. **`RoleWord[R]` (`64`-bit CAS via Gate):** `Vacant`, `Held(holder, epoch)`, `Handing(from, to, epoch)`.
3. **`OwnershipWord[Chunks]` & `DeviceEntry[Devices]` & `IdentifierWord[Seg × 65536]` (`64`-bit CAS via Gate):** `None`, `Free(owner)`, `Taken(owner, gen)` with `CHECK_MUL` parity check (`abi/src/machine.rs:276`).
4. **`GateWord[Chunks]` & `PageClass[Pages]` & `RunGrantTable[N][GRANTS]` & `UseTable[N][GRANTS]` (Single-Writer by Owner Gate, cleared only by `R6`):** Note a **`RunGrantEntry` (`128` bytes)** adds `base_chunk: u64` and `chunk_count: u16` (`1..=E`) replacing single-frame granularity; `UseEntry` (`32` bytes) tracks `map_count` (`u32`) per grant.
5. **`NotifyGenTable[N][NOTIFY_SLOTS]` (`8` bytes/notify slot, e.g., `1024` notifies/node = `8 KB`/node; Single-Writer by Owner Gate, zeroed in `R6`):** Stores `(node_gen: u32, serial: u32)`. Allows any sender node to verify `(node_gen, serial)` locally with one read (`0` locks, `0` grants) before enqueueing `StatelessSignal`.
6. **`CoreBeacon[N]` & `NodeBeacon[N]` (Single-Writer by Core/Node):** `heartbeat`, `idle_until`, `parked`, `panic`, `save_seal`, `acked[N]`, `maps_of` bitmask, `observations[8]`.

### 4.2 Shape D Invariants

1. **All Existing Safety Invariants Retained (`model/src/system.rs:501-655`, invariants `53–87`):**
   - `I58` (`map_count` == sum of leaf mappings), `I59` (all table pages match `PageClass`), `I71–73` (no stale/cross-self `Run-Grant` use), `I80` (disjoint chunk blocks), `I81–87` (IOMMU context entries never name dead generations, unit role exclusivity, valid member transitions, ≥ 1 live node).
2. **D-Specific New Safety Invariants:**
   - **D-Inv1 (Run-Grant Boundedness & No-Leak):** Every active `RunGrantEntry` covers `[base_chunk, base_chunk + chunk_count)` where all chunks read `Taken(granter, granter_gen)` and `1 <= chunk_count <= E`. `memory_give` refuses if any chunk in the run is covered by any `Live | Revoking | Pinned` `RunGrantEntry`.
   - **D-Inv2 (Stateless Signal Soundness):** A `StatelessSignal` packet delivers bits to `notify_id` if and only if `NotifyGenTable[to][notify_id] == (member[to].generation, notify.serial)` at delivery time; revoking or deleting a `notify` increments `notify.serial` atomically with `NotifyGenTable[me][notify_id]`, so no subsequent signal with an older serial ever sets a bit.
   - **D-Inv3 (Lazy Aspace TLB Coherence):** No thread on core `C` holds a TLB entry for `(va, aspace_id)` with higher permissions or stale PA after `aspace_unmap` or `aspace_protect` returns on home `H`, *unless* `C` has entered `Fencing` (`R0` ended wait with `gone`, and `R2`/`R3` prevents reuse of `H`'s memory until `C` is fenced/dead). Added mappings may fault harmlessly and resolve synchronously in `C`'s kernel (`Adds::Lazy`).
   - **D-Inv4 (Uniform Sender & Ring Order Safety):** Every inter-kernel ring is strictly FIFO per `(from, to)` pair with pre-allocated sender credits; `SenderCheck` runs before any state mutation.
3. **Liveness Invariants (`liveness.rs:1-16`):**
   - Under fair scheduling of live nodes' recovery reserves (`1/64` core) and fenceable cores (Class 1/2), every crashed node reaches `Dead`, every unit role reaches `Held(live_node)`, `>= 1` live node stays active, and no thread remains stuck in `Wait::Unit`, `Wait::AspaceAck`, or `CapRevoke(Again)` once the grantee/target dies.

### 4.6 Risks of Shape D & Falsifying Experiment

**Risks of Shape D:**
1. **Cross-core synchronous RPC must live in user space:** Userland components across cores lose kernel `Call` budget lending (`D-039` across cores). While [`wasm-abi.md:128`](/Users/btw/Documents/repos/Docs/architecture/wasm-abi.md#L128) relies on async WIT components and services have 1 thread/core (`D-028`), any native workload with frequent cross-core synchronous RPCs to a single-threaded service pays user-space ring + `Signal` wake-up overhead (`srv`: `9.60 µs` vs `8.45 µs` when single-threaded/split, [`results-mac-m5.md:994, 1026-1029`](/Users/btw/Documents/repos/dodos-kernel)).
2. **Thread migration without kernel `thread_move`:** Suspending, reading `REGS_WORDS` + feature state, and resuming on another core resets the local EDF/CBS context window on the target core instead of preserving exact remaining `(r, d)` across cores automatically (`kernel-interface.md:611`).
3. **Novel mechanisms unprototyped:** `Run-Grant` coalescing, `NotifyGenTable`, and in-kernel `Adds::Lazy` minor-fault handling add new gate-check invariants (`D-Inv1..D-Inv3`) that have not yet been model-checked or benchmarked on x86-64.
4. **Native multi-threaded heavy unmap workloads:** If a 16-thread native process unmaps/protects shared memory concurrently across all 16 cores at extreme rates (`10%+` changes), home-node serialization + peer IPI acks in Shape D will lag behind a fine-locked shared `aspace` (Shape C).

**Falsifying Experiment (What Would Prove Shape D Wrong):**
Build two minimal bare-metal prototypes on the **Intel Core i5-14600KF (`6P+8E`)** with `WRSSQ` write-gate, real IPIs, real `INVLPG`/`INVPCID`, and real `1`-ns TSC timing, running:
- **(E1) Mixed Native `aspace` Stress:** `14` pinned threads (`6P + 8E`) running Ladybird/inference-like allocation, mapping, `mprotect` (JIT/GC barrier), and `unmap` across `4 GiB` (`1%` and `10%` unmap/protect ratios, **including** multi-range `cap_revoke` and table-page frees).
- **(E2) Fault Containment + Recovery:** Inject panics and `cap_revoke` storms on 1 P-core and 1 E-core under both prototypes while measuring `Frame`-class compositor `8.3 ms` deadline misses (`scheduling.md:49`) and formal Verus/TLA+ proof closure.

**Shape D is falsified if:** (1) `Adds::Lazy` minor-fault overhead plus home-serialized `AspaceInvalidate` causes Shape D to trail Shape C (`Unmaps::Range` + `cap_revoke` subtree locking) by **more than `30%`** on realistic mixed map/unmap/protect throughput **while** Shape C successfully bounds `cap_revoke` duration (`D-042`) and passes deadlock/P+E `Frame`-class deadline gates, **OR** (2) hardware `MWAIT` in-place deep sleep with unit-role handoff fails to match D-108 power targets within `5%` on the 14600KF idle suite. Otherwise, keeping kernels strictly lock-free per core (Shape D) dominates on simplicity, verification tractability, failure isolation, 2-to-64 core scaling, and common-path tail latency.
